# 包工头回归用例与维护纪律

本目录是维护 skill 用的，不是 skill 运行时读取的内容。

## 为什么要有用例

包工头的规则大多来自实战事故，一条条补上去。补得多了，会出现两种问题：新规则和旧规则互相打架，或者某条规则是针对当时的模型写的，换代后反而让模型过度执行。只凭“用一段时间看看”分不清改动是变好还是变坏。用例集就是每次改 skill 之后都能重跑的回归检查。

思路取自 Anthropic 在 Code w/ Claude 2026 的演讲《The prompting playbook》：先有用例、建立基线、每次只改一处、改完全量重跑。

## 用例构成

`evals.json` 采用 skill-creator 的格式，每条用例有一个场景提示和几条可判定的通过标准。按三类组织：

| 类型 | 作用 | 用例 |
|---|---|---|
| 对照 | 本来就该过，用来发现改动引入的回归 | 1、2 |
| 已知易错 | 以前出过错、或分诊边界容易判错的情况 | 3、4、5、6、12、14 |
| 必须拦下 / 交人 | 必须走完整流程、先问用户或守红线的情况 | 7、8、9、10、11、13、15 |

用例都是单条回复：提示里写清前情，要求给出第一条回复，需要动手的步骤用文字说明，不实际执行。所以它测的是判断（分诊、升级、该不该问、该不该唤起），不测施工质量。

## 怎么跑

用 skill-creator 跑本目录的 `evals.json`，把当前版本和上一个提交的 SKILL.md 各跑一遍对比通过率。每条用例建议跑 3 次以上，同一条结果时好时坏的，按不稳定处理，不算通过。

改动后有用例从通过变成失败，先读失败的输出，判断是 skill 的问题还是通过标准写得不准，再决定改哪边。

## 维护纪律

改 skill 时按以下顺序：

1. **出了问题先补用例**：把这次的失败写成一条用例和一行通过标准，确认当前版本确实不过。
2. **想清楚能不能推广**：这次的失败是不是一类问题的一个例子，用例和改法按这一类写，不只修眼前这一条。
3. **优先改结构，不加强调**：能用模板字段、检查清单、脚本或工具做到的，不加“必须”“不得”“一律”；不堆长长的禁令清单。
4. **一次只改一处**：改完全量重跑，没有回归再提交。
5. **写明依据和时间**：新规则后面写“依据”（哪次事故或用户哪句话）和加入日期，方便以后换代时判断还需不需要。`references/foreman-workflow.md` 已有“依据”，新规则照此补上日期。
6. **两头的后果都写**：规则如果只写了一边的代价（例如只写打扰用户的代价），模型会一味往另一边偏。写规则时把另一边的代价也写上，或者配一条反向用例（参见用例 13 和 14）。

## 观察项

以下规则只写了一边的代价，目前没有出问题的证据，先不改，跑用例或实际使用中留意：

- “拿不准时按不唤起处理”：没写漏唤起的代价。用例 13、14 从两个方向各测一次。
- “子 agent 测试省着跑”：没写漏测的代价。
- “汇报不超过 300 字”：字数限制对不同模型影响不同，可能把关键信息挤掉。

## 待办

- **用钩子拦截子 agent 的危险 Git 命令**：任务书里禁用 `git add .`、`stash`、`reset` 等 7 条命令，现在只靠文字。Claude Code 可以改用 PreToolUse 钩子直接拦下，比文字可靠。没做的原因：钩子装在用户级配置里会对所有会话生效，用户自己的会话也会被拦；要只拦子 agent，得先确认钩子输入里能区分主会话和子 agent。Codex 没有对应机制，那边仍保留文字禁令。
