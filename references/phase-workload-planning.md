# AI 开发分期与工作量规划

生成或评审分期开发文档时必须使用本工作流。分期的首要目的，是把复杂开发任务拆成 AI 能在单个窗口内稳定完成、独立验收、随时中断恢复的小问题；不是按产品菜单、前后端层级或业务模块机械切块。从无到有且有界面时，视觉原型是需求发现期，施工顺序上必须先于正式实现期；详细规则见 `references/visual-first-workflow.md`。

**全部期次一次写完。** 视觉确认是跨会话的长动作，分期文档不为它停笔：期 0 到期 N 在同一次输出中生成，用一条视觉确认门槛线区分“施工可以立即开始”和“确认并复核后才能开始”。停笔等确认会让需求悬空、上下文膨胀，是本工作流明确要避免的失败模式。

## 一、分期定义

把每一期视为一个 **AI 执行单元**：

- 只解决一个主要问题，允许包含为解决它不可缺少的配套任务。
- 完成后留下可验证的代码、测试、调研结论、接口契约或迁移结果。
- 开始条件、输入、依赖和完成标准明确，不依赖上一窗口的聊天记忆。
- 结束时系统处于可构建、可验证、可继续开发的安全状态，不留下无法运行的半成品。
- 与前后期有关联，但依赖通过代码、文档、阶段标签和交接记录传递。

一期不必单独形成完整的用户可见功能。只要它解决了独立技术问题、降低了后续不确定性，并且结果可以独立核对，就可以成为一期。不得为了“每期都有页面效果”把大量地基、接口、页面和测试塞进同一期。

但每一期必须属于一个**交付包**。交付包是用户能实际用上的业务结果，期次只是完成它的 AI 执行单元：

- 交付包写清“做完后谁在哪里能做什么”，并能让用户实际操作一次来验收。
- 一个交付包通常 1–3 期，最多 4 期；规划时就超过 4 期，说明交付包太大，先把交付包拆小（按用户能分别用上的结果拆），不是把期次拆得更细。
- 每期写明所属交付包，以及做完本期后离交付还差什么。
- 只产出“准备 / 证明 / 审计 / 事实读取”、没有下游在同一交付包里直接使用的期次，不得单独成期；会决定方案选择的调研期除外。

依据：一个团队后台项目只按单期负载评分、不设交付包约束，原 17 期被反复拆成约 80 份期次文档、编号拆到第 7 层；施工约 20 小时、验收 30 个底层单元后，用户仍没有一个能实际用上的新功能。

## 二、拆期前准备

0. 先列交付包：从主需求文档的最终期望效果出发，列出用户能分别用上的业务结果，排出纵向切片顺序——门槛线之后第一个交付包应是最短的真实端到端链路（真实页面接上真实后端），后续交付包在它的基础上逐步加深。
1. 从已准入范围中列出任务原子：现状调研、业务规则确认、契约设计、代码改动、数据变更、迁移、测试、清理和文档同步。
2. 标记每个任务原子的前置依赖、影响模块、未知信息、风险和验收方式。
3. 先画单向依赖顺序，再组合成候选期次；不要先按“前端期 / 后端期 / 优化期”命名后硬塞任务。视觉原型期不是机械按层切块，而是为普通用户建立需求沟通锚点。
4. 按 `references/visual-first-workflow.md` 判定是否需要期 0 技术探针和期 1 前端原型；需要时在期次序列上划出视觉确认门槛线，豁免时写明事实依据。
5. 对每个候选期次做六维评分，并在输出文档前完成拆分或合并；门槛线两侧的期次都要写完，不因等待确认而少写。
6. 只有当现状不清会直接导致实现方向可能错误时，才创建调研 / 业务确认期。该期必须产出可引用的现状地图、证据、已确认决策和后续入口，不能只是“先看看代码”。

## 三、六维工作量评分

评分用于比较 AI 单窗口执行负担，不是人工工期或小时估算。每个维度记 0–2 分，总分 0–12。

评估从“读取核心材料、理解业务事实”一直到“实现、验收、填写交接并完成备份”的整期负担，不能只看预计代码量。调研、用户确认、跨模块检索、迁移验证和失败排查都属于工作量。

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 变更面 | 仅文档 / 极小局部 | 一个聚焦模块或少量紧密相关文件 | 多模块、广泛文件或需要同步替换旧实现 |
| 跨层与依赖 | 单层、无新依赖 | 两层联动或复用一个稳定依赖 | 三层以上、新依赖、异步链路或跨项目协作 |
| 业务 / 技术不确定性 | 规则和代码入口已明确 | 需要聚焦阅读或少量确认 | 需要调研、第三方验证、会改变方案的用户决策，或视觉形态尚未确认 |
| 数据 / 安全 / 可逆性风险 | 无状态或容易回退 | 配置、数据格式或权限有局部变化，或有备份可回退的数据迁移 | 鉴权、计费、密钥、不可回退的删除或无法备份的迁移 |
| 验收复杂度 | 一个聚焦检查即可 | 多个成功 / 失败场景和直接回归 | 多环境、端到端、迁移回滚或长链路验证 |
| 上下文负载 | 一个局部模块和少量材料 | 多个相关模块 / 规范，需要持续对照 | 跨项目、大量历史材料或多个业务域同时进入上下文 |

评分后应用：

- **0–3 分：偏轻。** 单一期的小改动可以保留；多期方案中的轻量期原则上并入相邻期。
- **4–7 分：建议区间。** 作为普通开发期的负载提醒，不是质量证明。
- **8–12 分：过重。** 输出文档前必须处理，不能只标“高风险”后原样保留；按第五节“超标处理顺序”先减负、再换方案、最后才拆。

唤起时的分诊（`SKILL.md`“先分诊”）也用这把尺子：约 0–3 分且无大活条件为小活，直接做；约 4–7 分且无大活条件为中活，速办派工；约 8 分以上或命中大活条件，走完整流程。

评分只衡量 AI 单窗口负担，不是越细越安全。风险维度天然偏高的期次（钱、鉴权）不靠无限拆分降分，而靠限定范围和监理审查控制风险。

以下情况不看总分也要处理：

- 不确定性为 2：先完成聚焦调研 / 确认，或把未确认分支移出实现期。界面形态未经确认时，先按视觉先行工作流制作原型；技术事实阻塞原型时只允许先做最小期 0 探针。
- 数据 / 安全 / 可逆性风险为 2：不得与无关功能混在一期；迁移、鉴权、计费、密钥或删除要有独立验证与回退边界。
- 上下文负载为 2：先精简必读材料（交接只读结论、不读长流水），仍高再按模块、契约或依赖顺序拆，并强化阶段交接。上下文负载常常是文档膨胀造成的，拆期会产生更多文档，反而让下一期负载更高。

## 四、视觉先行、前端原型期与确认门槛线

完整读取 `references/visual-first-workflow.md`，本节只保留拆期约束：

- 从无到有且有界面时，视觉原型是正式实现前的强制需求发现期。
- **期 0 到期 N 的全部期次在同一次输出中写完**，不因等待用户确认而中断；未经视觉验证的结论标注“待视觉确认复核”，不留白。
- 期次序列必须有一条显式的**视觉确认门槛线**：门槛线之前是原型和前端可见效果，之后是后端、数据、鉴权、集成和迁移。总览表要能一眼看出门槛线的位置。
- 技术事实会阻塞页面成立时，可以先设最小期 0 探针；探针不得扩展成正式底座，结束后仍进入原型期。
- 期 1 原型写在正式前端目录，使用可替换 mock，覆盖正常、空、加载、失败和关键动作，并隔离生产构建。
- 期 1 文档必须写“本地预览与用户确认”：真实启动命令、本地预览入口、请用户走的测试路径和放行条件。
- 门槛线之后的每一期，在“前置状态”写明依赖期 1 视觉确认通过、修改项闭环，并留出复核结论的填写位置。
- 用户确认必须绑定提交号或版本标识、页面入口和截图 / 录屏；确认与复核未完成前不得开始门槛线之后的施工。
- 豁免只适用于无界面、明确 BUG 且没有新增视觉结构或交互决策、或完全复用已确认交互的升级。

## 五、拆分与平衡规则

按以下顺序选择边界，不要求全部使用：

1. **先看见再施工**：本次涉及新建或明显改变用户可见界面时，先出可交互前端原型并取得用户视觉确认，再建后端底座（豁免条件见第四节）。这是施工顺序约束，分期文档本身一次写完。
2. **先认知再施工**：现状或业务规则不清时，先产出证据和决策，再进入编码。
3. **先固定契约再接入**：先稳定数据结构、接口契约或内部边界，再让调用方接入。
4. **先最小技术闭环再扩展**：先跑通一个可验证路径，再增加已确认场景。
5. **先新链路再迁移 / 清理**：新实现稳定后再迁移数据或删除旧体系。
6. **先低风险后高风险**：把不可逆、高权限或外部依赖操作隔离到可单独停下的一期。

每个普通开发期同时满足：

- 一个主要问题，标题直接描述要解决的问题。
- 3–6 个核心任务包；超过 6 个时重新判断是否混入多个问题。
- 有明确输入、输出、依赖、验收和“本期不做”。
- 完成后可构建 / 可运行 / 可检查，不把无法验证的半成品交给下一期。
- 后一期只依赖前一期的持久化产物，不依赖聊天记忆。

平衡全部候选期次：

- 普通开发期尽量都落在 4–7 分，最高分与最低分差不超过 3 分。
- 某一期 8 分以上时必须处理；不能用“这是核心期”作为超载理由。
- 多期中的 0–3 分轻量收尾应并入相邻期，除非它是有独立价值的调研确认、数据迁移、破坏性清理或高风险验证检查点。
- 不为追求分数平均而增加范围外工作，也不创建没有独立产物的占位期。

### 超标处理顺序（8 分以上，或执行中实际超过 7 分）

按顺序尝试，前一步能解决就不走下一步：

1. **减负**：删掉与真实风险不相称的防御、验证和范围外工作（见下方“相称原则”），重新评分。
2. **换方案**：有没有更简单、业内常规的做法能达到同样的业务结果（例如迁移用“备份 → 迁移 → 核对 → 可回退”，不自造证明体系）。改变方案影响业务结果时交用户确认。
3. **拆一层**：仍超标才拆，原期 N 最多拆成 Na / Nb / Nc，每个子期仍须属于同一交付包、有下游直接使用的产物。
4. **熔断**：子期仍超标、需要第二次拆分时，不得继续拆成 Na1、Na1a；停下来按 `references/foreman-workflow.md` 第十五节复盘，交用户决定。

### 相称原则

防御、校验、边界测试和“证明”只做以下四类依据支持的部分：

- **真实数据量级**：查实过的现有数据规模和增长预期（例如“单条话术最长约 2 000 字、全库约 3 000 条”），不按理论最大值设计。
- **真实事故**：项目里发生过、或同类系统常见的问题。
- **用户明确要求**：有原话或决策编号。
- **钱和权限的直接攻击场景**：少收钱、多发额度、越权访问、串号。

不在这四类里的极端情况（超大单字段、罕见编码、理论并发缝隙等）写进“已知限制”，说明影响和触发条件，不实现、不单独成期。依据：同一个团队后台项目为个人话术迁移专门做了 4MB / 16MB 单条字符串、孤立编码字符、句柄回收的逐段审计，拆了约 20 份期次文档，迁移本身仍未发生；用户追问“你是不是过度防御了”。

不要为了省事按前端、后端、数据库机械分期。**要区分三种情况**：

- 禁止：为图方便把同一批工作按技术层切成“前端期 / 后端期”，两边没有各自要解决的独立问题。
- 鼓励：第四节的前端原型期，为在投入底座前消除视觉不确定性而设立的风险隔离期，必须排在实现期施工之前。
- 必需：由视觉确认门槛线划出的“门槛前 / 门槛后”边界。这条线上存在一个真实的用户确认动作，它决定后续方案是否成立，因此是有效边界，不算机械切块。

判断标准是这一期有没有独立要解决的问题和独立的验收结论，而不是它属于哪一层。门槛线之后仍按独立问题、依赖和工作量拆，不允许把后端工作再机械切成“接口期 / 数据库期 / 联调期”。

如果拆开后任一期无法独立验证或会使系统长期不可用，就按可验证契约或最小技术闭环重新组合。同一项业务能力可以拆成多个技术执行期，但受交付包上限（最多 4 期）和“只拆一层”约束。

## 六、上下文边界

每期提示词都写清：

- **核心必读**：主需求文档中与本期直接相关的章节、上期交接记录、2–6 个最关键代码入口或规范。
- **按需读取**：只有出现指定问题时才读取的次要材料。
- **禁止泛读**：不要让执行 AI 为“了解全局”一次性加载全部仓库、全部历史需求或所有期次。
- **上下文负载结论**：低 / 中 / 高及理由；“高”必须重新拆分，不能直接进入开发。

主需求文档保存完整业务背景；单期提示词只摘录本期必须知道的已确认结论，并通过路径回指原文，不重复粘贴整份需求。

## 七、阻塞、恢复与动态拆期

每期在动手前列出可能改变方案的阻塞点和确认时机。开发中出现以下任一情况时，停止扩张实现：

- 新发现会改变业务结果、权限、计费、数据归属、删除范围或系统边界。
- 实际影响模块、阅读材料或任务包明显超过本期评估。
- 验收链路比计划多出新的环境、迁移或外部依赖。
- 需要用户决策才能选择互斥实现。

暂停时在本期文档填写“阻塞快照”：

```markdown
## 阻塞快照（仅阻塞时填写）
- 已完成：
- 尚未完成：
- 发现的事实与证据：
- 需要用户决定的问题：
- 不同选择的业务影响：
- 当前代码 / 数据是否处于安全状态：
- 恢复开发的第一步：
```

不要在长对话里反复重述全部背景。用户确认后，把决定写回主需求文档和本期交接记录，再继续。

如果实际工作量超过 7 分，先按第五节“超标处理顺序”减负、换方案；仍超标才停在可验证边界，缩小当前期并把剩余任务拆成新期次（包工头施工时用 `N b` 编号，如 `10b`，见 `references/foreman-workflow.md` 第四节第 5 条）。`N b` 不得再拆成 `N b1`；需要第二次拆分时触发熔断。只在缩小后的当前期已经形成独立可验收结果时才把它标记完成；未开始的后续期可以重新编号，已经完成的期次和 Git 标签不得改名或覆盖。

## 八、阶段交接

每期验收后、Git 备份前，在本期文档填写“阶段交接记录”，并把它纳入本期提交：

```markdown
## 阶段交接记录（完成后填写）
- 所属交付包与离交付还差什么（业务话）：
- 本期解决的独立问题：
- 已确认的业务事实：
- 关键实现与取舍：
- 变更文件 / 模块：
- 接口、数据结构或配置变化：
- 验收命令与结果：
- 未完成项与明确不做：
- 遗留风险 / 已知问题：
- 需用户实测、拍板或提供材料的事项：
- 试用准备（需要唤起试用的期次必写）：启动方式、入口、测试账号与演示数据、是否已真启动确认能打开：
- 需包工头执行的线上操作：
- 供审查的重点文件清单（涉及钱、鉴权、密钥、删除时必写）：
- 下一期开始前必须满足：
- 本期阶段标签：
```

前端原型期的交接记录额外写清四项：本地预览是否已实际交用户打开测试、用户确认结论、修改项闭环状态、门槛线之后期次的复核结论（无实质变更 / 已更新哪几期 / 已作废重拆哪几期）。缺这四项时后续期次不得开工。

不要在交接记录里写提交号后再制造循环提交；下一期可以通过阶段标签查询精确版本。下一窗口先读上一期交接记录和阶段标签，再读本期核心材料。

交接记录写结论，不写过程流水：正文控制在约 60 行内；文件哈希、执行次数、逐次观察记录等技术证据不进正文，确需留存时放进单独的技术附录或忽略目录，正文只写“已核对、结论是什么”。交接越长，下一期上下文负载越高。

## 九、输出前检查

1. 是否先拆任务原子和依赖，再组成期次。
2. 涉及新建或明显改变用户可见界面时，第一期是否为前端原型期；判为豁免时是否写明命中第四节哪一条豁免条件与依据。
3. 期 0 到期 N 是否一次写完，没有因为“等用户确认视觉”只交付前端期就停笔。
4. 期次总览是否能一眼看出视觉确认门槛线的位置，门槛线之后的每一期是否在前置状态回指放行条件。
5. 前端原型期是否写了“本地预览与用户确认”：真实启动命令、预览入口、用户测试路径和放行条件。
6. 前端原型期是否要求写在项目正式前端目录、用可替换的模拟数据层、核对过关键数据的形态（字段是否存在 / 大概多少条 / 大概多久出结果，内容不管）、覆盖空 / 加载 / 失败状态，并产出《前端确认记录》。
7. 是否给每一期写出六维评分依据，而不是只写“高 / 中 / 低”。
8. 是否存在 8 分以上重期、无理由的 0–3 分轻期，或普通期最高分与最低分相差超过 3。
9. 是否把调研与大量实现、数据迁移与无关功能、旧体系清理与新链路建设塞在同一期。
10. 门槛线之后是否又按“接口期 / 数据库期 / 联调期”机械切块。
11. 每期是否只有一个主要问题、3–6 个任务包，并能独立验证。
12. 每期是否有核心必读、按需读取、阻塞快照和阶段交接记录。
13. 下一期是否可以只凭仓库、主需求文档、上期交接和阶段标签继续，不依赖旧聊天上下文。
14. 是否先列了交付包；每期是否写明所属交付包；单个交付包是否不超过 4 期。
15. 门槛线之后第一个交付包是否是最短的真实端到端链路；是否把“页面接真实接口”集中放到了最后几期。
16. 是否存在多层拆分编号（如 Na1）或只产出准备 / 证明 / 审计、没有下游直接使用的期次。
17. 每项防御、校验和边界测试能否回指相称原则的四类依据；极端情况是否写进了“已知限制”而不是任务清单。
