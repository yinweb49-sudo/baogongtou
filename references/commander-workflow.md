# 总指挥施工工作流

需求文档和期次写完后，由总指挥带子 agent 一期一期做完。总指挥只派活、收汇报、和用户沟通、维护进度；代码由开发子 agent 写，独立审查由审查顾问做。角色与模型见 `references/model-roles.md`，任务书模板见 `references/dispatch-brief-template.md`，交接模板见 `references/commander-handoff-template.md`。

本工作流来自一个 30 余期真实项目的 6 轮施工记录，每条规则后面都有对应的事故或实测依据。

## 一、什么时候进入施工

满足以下全部条件才开始派活：

1. 主需求文档和期次总览已写完，`review-checklist.md` 自检通过。
2. 用户明确说开工（“开始开发”“按期次施工”“从期 N 开工”等）。只要求写文档时不施工。
3. 当前期次的前置状态满足；位于视觉确认门槛线之后的期次，门槛已放行。
4. 项目档案“总指挥施工”一节已填写；缺失时按默认值执行，并在第一次汇报里告诉用户用了哪些默认值。
5. Codex 下已把角色文件放进 `.codex/agents/`（见 `model-roles.md` 第四节）。

接手已有施工（换窗口、换电脑、上下文过长后重开）时，先读最近一份《总指挥工作记录》和期次总览 README，按其“开场提示词”和待办清单继续，不依赖旧聊天。

## 二、总指挥的职责边界

**总指挥做**：

- 读期次总览、上期交接，判断能否开工、能否并行、是否需要拆段。
- 按模板写任务书并派活；收汇报、读状态文件。
- 把子 agent 遇到的业务问题翻成大白话问用户，把用户原话原样转回子 agent。
- 核对交付物存在：提交号、标签、阶段交接记录是否已写。只核对“有没有”，不重做验收。
- 更新期次总览 README 的状态列；写《总指挥工作记录》。
- 交给用户亲手执行的命令，先自己逐行核对再交出。

**总指挥不做**：

- 不写产品代码，不改测试，不替子 agent 跑测试。
- 不额外派“核实子 agent 汇报”的小 agent；对结论有争议时才派审查顾问仲裁（见第六节）。
- 不把口令、密钥写进任务书或转给子 agent。
- 不修改开发工具自身的权限设置。

**依据**：总指挥用的是最贵的模型，亲自写代码会快速耗尽额度和上下文；只派活时，一个总指挥会话可以连续带完 8–10 期。

## 三、每一期的循环

### 1. 开工判断

- 读 README 期次总览、本期文档的“前置状态”“预计阻塞点”、上一期“阶段交接记录”。
- 本期文档写于较早时间、且中间已有多期施工时，任务书第一步加“先核对文档与代码现状的差异，不一致以代码为准并上报”。依据：文档写完两天后开工的一期，要删除的文件仍在被使用、文档声称已有的测试实际不存在；子 agent 按“以搜索为准”核对后如实上报，避免了误删。
- 判断本期是否命中：需要用户确认的决定（第四节）、红线操作（`model-roles.md` 第五节）、需要独立审查（第六节）、可与其他期并行（第五节）。
- 用户中途新定的小改动，作为“附加任务”交给紧接着的那一期开工时先做，单独提交，由该期负责记进需求证据。

### 2. 派活

按 `dispatch-brief-template.md` 写任务书。任务书只给路径和必要摘录，不粘贴整份需求文档。

### 3. 等待与收汇报

- 子 agent 后台运行，完成后会通知总指挥；不轮询，不提前臆测结果。
- 收到汇报后先读状态文件。依据：曾出现子 agent 多次“完成”但汇报没有送到总指挥的情况；要求同时写状态文件后再未丢失。
- 汇报里有“阻塞快照”时，按第四节处理；有“需用户亲手执行”的步骤时，核对后转交用户。

### 4. 收尾

- 核对：本期提交、阶段标签、阶段交接记录、推送结果（按项目保存策略）。
- 更新 README 期次总览的“状态”列，写清遗留项，例如“已完成（录屏待用户实测）”。
- 命中审查条件的期次，派审查顾问（第六节）。
- 向用户发一条简报（格式见第七节），再进入下一期。

### 5. 现场拆期

子 agent 汇报实际工作量超出、或追加内容后评分超过 7 分时，停在可验证边界，把剩余部分拆成 `N b` 期（如 `10b`），在 README 总览里加一行，标签用 `phase-10b`。涉及钱的期次在任务书里写明“宁可拆，不要赶”。已完成的期次和标签不改名。

## 四、需要用户确认的期次

### 拆两段派

本期需要用户先拍板（删除清单、规则缺口、口径选择）时：

1. **第一段只读**：子 agent 只读代码、产出清单或选项，写进状态文件，不改代码。
2. 总指挥把清单翻成业务话交用户确认。
3. **第二段施工**：续派同一个子 agent（它已有上下文），把用户原话原样一并转过去，由它记进需求证据并施工。

依据：一期清理任务用这种方式，只读核对约 7 分钟，确认后续派施工约 20 分钟，没有返工。

### 子 agent 中途阻塞

- 子 agent 停在可恢复状态、填好阻塞快照后上报。总指挥不替用户决定。
- 用户的答复里有没看懂的题：先按总指挥建议的默认值继续施工，不阻塞；在交接和需求证据里标“待用户最终确认”，解释清楚后再补。
- 用户的答复改变了已确认的决定时，先更新决策台账，再续派。

## 五、并行

承诺并行之前，对照两期文档的“核心代码入口”和“任务清单”，确认没有同层、同文件的改动。

**可以并行**：

- 一方只改前端 / 客户端，另一方只改后端 / 服务端；
- 一方只读（核对、审查），另一方施工，且读的范围不是对方正在改的文件。

**不能并行**：两期改到同一层的同一批文件。依据：两期都要改同一个客户端接口文件，同一目录两个 agent 同时改，一方改到一半另一方就编译失败；改为先后执行，额度消耗不变，只多花约 20 分钟。

**并行时的地盘规则**：

- 任务书写明各自的目录地盘，提交时只列自己地盘内的路径；新文件先 `git add -- <具体路径>`。
- 需求证据、主需求文档、README 总览这类共用文档，同一时间只指定一方写；README 状态由总指挥在两边都完成后统一更新。
- 推送冲突时先 `git pull --rebase`，不强推。
- 端口按用途分开：用户走查、子 agent 联调、子 agent 自测各用各的端口，写进项目档案；不结束别人的进程。
- 需要干净副本联调时，用 `git worktree add` 从上一期标签建副本，换端口运行。
- 客户端期与服务端期并行时，客户端只能对着模拟后端测；收尾时补一次真实联调。

## 六、独立审查

### 必审

- 涉及钱的期次（下单、支付、退款、扣费、额度、席位）做完后，派审查顾问独立审查。依据：同一项目先后两次审查各挖出 1 个高危问题——升档少收钱、撤销非最近一笔续费会白送席位——两处开发子 agent 的测试都没覆盖，其中一条测试甚至把攻击场景当成正常用例。
- 鉴权、密钥、删除、数据迁移相关期次，按风险决定是否审查，写进 README 的施工基线。

### 仲裁

- 用户或总指挥怀疑子 agent 结论有误时，派审查顾问只读复核，把结论如实告诉用户，不迁就任何一方。依据：一次用户怀疑开发子 agent 误报，复核后证明子 agent 是对的。

### 做法

- 让开发子 agent 在汇报里附“供审查的重点文件清单”，审查任务书直接引用，审查通常约 5 分钟。
- 审查只读；任务书写明红线：只读源代码文件，不打开任何配置、证书和密钥文件。
- 结论要求带“文件:行号”和触发场景。
- 发现问题后另派开发子 agent 修：先写测试复现，再修复。
- 审查可以和下一期并行，前提是下一期不改被审查的代码；修复等下一期交回、被审代码无人在改时再派。

## 七、和用户沟通

- **业务语言**：先用具体场景讲清“现在是什么样”（例如“下载好新版本后要重启才能装上，按钮在账号菜单里”），再问要不要改。依据：两次把术语说得太抽象，用户没看懂，来回多问了一轮。
- **规则缺口先讲现状**：规则缺口背后往往是对现有机制理解不一致。先用例子讲清现在怎么算，再给选项和推荐。
- **用数字锁口径**：用户的回答改变了已确认决定时，用一道带数字的确认题锁定，例如“5 个席位、每席 100 点、只有 1 个人在用，最多能用多少点”。
- **不迁就**：子 agent 的结论经复核是对的，就如实告诉用户；用户的判断有误也直说，并给证据。
- **简报格式**（每期收尾一条，不超过 10 行）：

```markdown
期 N《名称》完成 / 阻塞
- 做成了什么：<业务话，一两句>
- 需要你做的：<亲手执行的步骤 / 要你实测的页面 / 要你拍板的问题；没有写“无”>
- 遗留：<待实测、待补录屏等；没有写“无”>
- 下一步：<期 N+1 名称，或等你答复>
```

## 八、轮次交接与上下文

总指挥会话也会变长。以下任一情况出现时写一份《总指挥工作记录》，结束本轮：

- 总指挥上下文已明显变重（多期汇报、多轮用户问答累积）；
- 用户要换电脑、换工具或暂停；
- 一个阶段性节点完成（例如门槛线放行、全部开发期完成、上线前）。

交接记录写在 `docs/<功能名称>/总指挥工作记录-第N轮-期X至Y.md`，模板见 `commander-handoff-template.md`。后一份只写本轮新增内容，前几份仍有效的部分用“见第 N 轮”引用，不重复抄写。最后附“新总指挥开场提示词”，用户开新窗口时粘贴。

额度管理按项目档案执行；档案没有要求时不主动询问额度。各期耗时、额度读数记进交接记录，供下一轮估算。

## 九、不支持子 agent 时的退路

工具不能派子 agent，或用户要求手动执行时：

- 每期单独开一个窗口，把期次文档全文和本期任务书一起作为初始提示词；
- 用户临时充当总指挥：开工判断、收尾核对、README 状态更新按本工作流第三节执行；
- 期次文档、阶段交接、检查点规则完全不变，随时可以切回总指挥模式。

## 十、施工纪律速查

写进每份开发任务书（模板已含）：

| 纪律 | 内容 | 依据 |
|---|---|---|
| 测试省着跑 | 开发中只跑与改动相关的测试；收尾全量只跑一次；失败只修失败项、只重跑失败项；不为“验证稳定性”反复重跑 | 用户要求控制额度；偶发失败用日志定位，不靠重跑 |
| Git 安全 | 禁止 `git add .`、`git add -A`、`stash`、`reset`、`clean`、`restore`、`checkout --`；只提交指定路径；附注标签显式写提交号 | 防止混入用户改动；还原类操作被权限拦截过 |
| 不许猜 | 拿不准就停在可恢复状态，填阻塞快照，写进汇报 | 用量口径类问题按要求不猜，留给真实调用核对，避免错误计费 |
| 不碰机密 | 不读、不打印、不转交真实密钥；需要时写成“由用户亲手执行”的命令清单 | 读密钥的任务书被安全规则整体拦下 |
| 汇报短 | 汇报不超过 300 字、大白话，同时写状态文件 | 汇报丢失 |
| 临时文件 | 临时构建目录放会话临时目录，用完即删；不在仓库外留目录 | 子 agent 删仓库外目录被权限拒绝，只能留给用户手删 |
| 测试副作用 | 测试会改写受版本管理的文件（如截图）时，子 agent 自己还原，或让测试写到忽略目录 | 冒烟测试改写了文档目录的截图 |
| 生产脚本 | 会动生产环境的脚本交给用户前，先做语法解析校验，再派审查顾问独立审查 | 部署脚本连续三次因编码问题失败，校验 + 审查后一次成功 |
