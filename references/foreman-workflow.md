# 包工头施工工作流

需求文档和期次写完后，由包工头带子 agent 一期一期做完。角色与模型见 `references/model-roles.md`，任务书模板见 `references/dispatch-brief-template.md`，交接模板见 `references/foreman-handoff-template.md`。

分诊为中活的**速办派工**不走本工作流的全套，按 `SKILL.md`“速办派工”执行：只用本文件第四节第 3 条（收汇报）、第九节（线上操作与凭据）、第十一节（叫停）和第十四节（施工纪律）；要拍板的事直接在对话里问，不建《待您决定》；不唤起试用（用户要求时除外）；不写期次总览和工作记录。速办中途升到完整流程后，才按本工作流全套执行。

本工作流按默认的**半自动模式**写：用户在场，要拍板的事、试用、熔断复盘、交接都会停下等用户。用户开启**全自动模式**后，这些“停下等用户”的环节按 `references/full-auto-mode.md` 第二节替代，其余规则不变。

本工作流提炼自一个 30 余期真实项目的 6 轮施工（含两台电脑交替开发、生产部署和上线验收）。每条规则后面的“依据”是当时的事故或实测。

## 一、包工头的定位

需求已经写清楚、拆成期次，开发阶段不需要再做大量设计和思考，所以写代码交给主力档模型；最强档模型留给需要判断的地方。

**包工头不做**：

- 不亲自写产品代码，不改测试，不替子 agent 跑测试，不做验收核验。
- 不额外派“核实子 agent 汇报”的小 agent。依据：第一轮开工时为确认模型版本派过一个，事后判定为浪费。
- 不把口令、密钥写进任务书或转给子 agent。

**包工头亲自做**：

- **规划**：排批次、判断并行、估算额度、决定停在哪里（第三节）。
- **查实再派**：任务书里会决定实现方向的关键事实（官方接口地址、参数、价格、报错码、合同主体等），由包工头先查官方文档核实，写进任务书，让施工队照着做、不用自己判断。依据：接入新模型服务商时这样分工，施工队一次做对。
- **沟通**：把子 agent 遇到的业务问题翻成大白话问用户，把用户原话原样转回子 agent。
- **线上操作**：需要凭据或会改动生产环境的操作，由包工头亲自执行（第九节）。凭据不能交给子 agent，而这类操作又需要随时判断。
- **核对交付**：提交、标签、阶段交接是否到位；只核对“有没有”，不重做验收。
- **维护进度**：更新期次总览 README 的状态列；每轮结束亲自写《包工头工作记录》，因为只有包工头手上的信息最全，转给子 agent 写反而要重述一遍。

**监理**（T1 档子 agent）只在三种情况介入：施工队卡住或遇到不确定的情况、涉及钱等高风险期次的独立审查、对某个结论有争议需要仲裁。它同样不写代码。

## 二、开工准备

新包工头接手、或开始一个新批次前：

1. **读交接**：最近一份《包工头工作记录》、仍然有效的前几份、期次总览 README、本批第一期的文档。按开场提示词的顺序读，不依赖旧聊天。
2. **查现场**：
   - `git status` 与最近提交。出现不是本流程产生的提交或改动（用户在别的窗口做的），先问用户，不要混进本期提交。
   - 换了电脑时，核对本机环境是否跟得上：依赖、开发数据库、本机密钥、工具版本。不齐就先派一个子 agent 只做环境准备和自检，不碰生产。交接记录里应有环境清单。
   - 用户自己正在改的文件（例如用户在调界面），与本批期次重叠时，先请用户提交，再开工。
3. **对文档**：期次文档写得较早时，先找出与现状不一致的地方：路径变了、旧规则已被用户新决定推翻、文档声称存在的东西其实不存在。被新决定推翻的旧规则，派一个子 agent 在所有受影响的期次文档里统一改掉；只是换了电脑导致的路径差异，不要批量改文档，在任务书里写一句“文档中写死的路径一律按本路径理解”；其余写进任务书“以代码为准”。依据：一份写于两天前的期次文档里，要删的文件仍在被使用、声称已有的测试并不存在；另一次用户授权复用某配置，推翻了多份期次文档里的旧禁令，统一改完才开工。
4. **确认模型可用**：按 `model-roles.md` 用系列名派活；Codex 下先把角色文件的型号填成当前可用的最新一代。依据：第一轮开工时工具版本太旧，主力档模型不可用，用户升级工具后才恢复。
5. **一次问清**：把本批开工前必须由用户决定或提供的事项登记进《待您决定》（第十节），列成编号清单，每项附建议，请用户按编号一次答复。依据：分散提问会让用户来回切换，按编号一次答复后当场开工。

## 三、批次规划与额度预算

### 分批计划

开工时给用户一张分批计划表，之后每轮按实际进度更新：

| 批次 | 交付包（做完用户能用上什么） | 期次 | 可并行的组合 | 停点与原因 | 需要用户的环节 |
|---|---|---|---|---|---|

- **停点**选在交付包结束处，即用户能实际用上一项功能（例如“主账号能在真实网页登录并管理成员”“账号体系完成”），不要停在某个功能做到一半，否则下一轮要重新理解。“服务端地基做完”不算停点，除非同一批次紧接着就能接上页面。
- 计划表按交付包排列，每个交付包写清做完后用户能用上什么；交付包之间先排最短的真实端到端链路，再逐步加深。
- 视觉确认门槛、需要用户实测、需要用户提供材料的环节，在表里标出来；这些地方本来就要等用户。
- 依赖链上的期次只能一期接一期做；能并行的组合按第七节判断后写进表里。用户问“为什么只派一个子 agent”时，用依赖关系解释（例如两期都要改数据库结构，并行会冲突）。

### 额度预算（项目要求时）

用户给了额度上限（例如“在这个 5 小时额度内完成，尽量不要超”）时：

- 用已完成期次的实际消耗估算剩余能做多少期，不凭感觉。记录每期子 agent 耗时，写进交接记录，供下一轮估算。
- 估算超出时，先收缩计划：缩到一个完整的功能环节就停，告诉用户“这一轮做到哪里停、为什么停在这里”。
- 设刹车线（例如 5 小时额度用到 75%、或离重置不到 40 分钟，就不开新的一期）。正在做的那一期先停到可恢复的位置、提交保存，再停。
- 实际消耗比预估少时，可以放宽到下一个功能环节，同样先告诉用户。依据：第一轮原计划做到期 4，前 4 期只用了 18% 额度，放宽后做到期 8，正好完成“账号体系”整个环节。
- 包工头看不到额度读数，只能请用户查看（例如 Claude Code 的 `/usage`）。用户明确取消这项要求后就不再询问。

没有额度要求时不主动询问额度，但仍记录耗时。

## 四、每一期的循环

### 1. 开工判断

- 读本期文档的“前置状态”“预计阻塞点”“施工安排”和上一期“阶段交接记录”。
- 判断本期是否命中：需要用户先拍板（第六节）、线上操作（第九节）、必审（第八节）、可与其他期并行（第七节）、需要先查实的外部事实（第一节）。
- 用户中途新定的小改动、上一轮遗留的小修复，作为“附加任务”交给紧接着的那一期开工时先做，单独提交，由该期负责记进需求证据。

### 2. 派活

- 按 `dispatch-brief-template.md` 写任务书。只给路径和必要摘录，不粘贴整份需求文档。
- 写明已知问题：以前就失败的测试、本期不该修的旧问题、永远不要提交的文件。依据：不写的话，子 agent 会在别人留下的问题上白白消耗额度。
- 给用户的进度里说明派了几个子 agent、各做什么、用的哪个角色。依据：用户会问“子 agent 是用什么模型干活的”。

### 3. 等待与收汇报

- 子 agent 后台运行，完成后会通知包工头；不轮询，不提前臆测结果。
- 收到汇报后先读状态文件。依据：子 agent 多次“完成”但汇报没送到包工头，要求同时写状态文件后再没丢过。
- 汇报里的“子 agent 自加的规则”（文档没写、它自己定的做法）要单独拿出来，附建议交用户拍板，不默认采纳。依据：先后有多条这样的规则，例如“默认模型不能直接取消默认”“席位数不能少于已加入人数”，都是交用户确认后才写进决策。
- 测试有偶发失败时，要求子 agent 记下是哪一项、查是不是本期造成的，不要反复重跑碰运气。

### 4. 收尾

- 核对：本期提交、阶段标签、阶段交接记录、推送结果（按项目保存策略）。
- 更新 README 期次总览的“状态”列，写清遗留项，例如“已完成（录屏待用户实测）”。状态列只写业务话，不超过约 40 字；不写文件哈希、执行次数、内部函数名。
- 一个交付包的最后一期完成、且属于第五节第 1 条的“大功能完工”时，包工头不问用户，直接按第五节唤起试用程序、发编号测试步骤和注意事项；用户反馈通过后再开下一个交付包。中间期次和小修小补不唤起，只在简报里带过。
- 命中必审条件的，派监理（第八节）。
- 给用户一条简报（第十节），再进入下一期。

### 5. 现场拆期

实际工作量超出、或追加内容后评分超过 7 分时，先按 `phase-workload-planning.md` 第五节“超标处理顺序”减负、换方案；仍超标才停在可验证边界，把剩余部分拆成 `N b` 期（如 `10b`），README 总览加一行，标签用 `phase-10b`。拆期边界可以预先写进任务书，例如“先做服务端与测试，界面超出工作量就拆 b 期”。涉及钱的期次写“宁可拆，不要赶”，但同样只拆一层。已完成的期次和标签不改名。

**只拆一层**：`N b` 不得再拆成 `N b1`、`N b1a`。同一原期需要第二次拆分时，触发第十五节熔断，停下复盘，不继续拆。

## 五、唤起试用与视觉确认门槛

用户试用是交付闭环的最后一步。把程序启动起来、打开到入口页、写好测试步骤，这些准备由包工头做完，用户只负责“点开就测”。

### 1. 什么时候唤起

**只在一个大功能完工时唤起**，即用户能完整用上一项新功能的时候：

- 原型期（视觉确认门槛线所在期）做完；
- 一个交付包的最后一期做完（必审的，监理阻断项修完之后），且这个交付包带来了新页面、新流程或主流程的明显变化。

**以下一律不唤起、不请用户确认**，只在简报里一句话带过，累积到下一次大功能试用时一起看：

- 交付包中间的期次（做完了用户也还用不上）；
- 小修小补：修 BUG、监理阻断项的修复、附加任务、文案、样式、个别按钮或字段的调整；
- 只改服务端、用户看不到变化的期次；
- 只有一期、没有新页面和新流程的小交付包：试用合并到下一个交付包，在下一次试用说明里加一步带过；它不触发等待，直接开下一个交付包。

拿不准算不算“大功能”时，按“不唤起”处理，在简报里写一句“这项可以顺手看，也可以等下一次一起看”。用户主动说“打开给我看看”时随时唤起，不受上面限制。依据：用户要求“测试一定是一个大的功能完工，不要小功能、小调整都频繁骚扰用户来确认”。

批次停点、轮次交接之前，有符合上述条件、做完但还没交用户试用的交付包时，先唤起再停。

唤起**不先问用户**：只在本机启动、随时可关、不花钱，属于第九节“默认由 AI 直接做完”的操作；由包工头亲自做，不派子 agent，因为包工头要知道程序开在哪、能随时关掉重开。依据：用户要求“开发完一轮功能包后主动唤起测试页面，不需要用户确认”；以前把启动命令交给用户自己跑，违背了“不要让我自己去终端运行”。

### 2. 怎么唤起

1. **取启动方式**：项目档案“试用唤起”一节 + 本交付包最后一期文档的“交付包试用说明”（原型期为“本地预览与用户确认”）。两处都没有时，从代码和配置核实，不猜端口和路由。
2. **关旧程序**：只关包工头自己上次启动的试用程序（启动时记下它的进程或窗口）。端口被不明程序占着时不结束它，改用项目档案登记的备用端口（没登记就用相邻的空闲端口），并在试用说明里写明换了地址。
3. **启动**：在用户走查端口、后台持续运行。工作区有别的期次做到一半的改动时，用 `git worktree add` 从本交付包的标签建副本启动，不把半截代码带给用户。
4. **确认能打开**：网页入口能正常返回、客户端窗口出现、命令行程序出现就绪提示。打不开不交给用户：依赖没装、端口冲突这类环境问题包工头当场处理；涉及代码的派施工队排查修好，再重新唤起。包工头只核对“能打开”，不替用户走测试步骤。
5. **打开到入口页**：
   - 网页：用系统默认浏览器直接打开到要测的那一页（Windows `Start-Process <地址>`，macOS `open <地址>`，Linux `xdg-open <地址>`）；
   - 桌面客户端：直接启动窗口；
   - 命令行程序：开一个新的终端窗口运行，停在等待输入处；
   - 手机端：有模拟器或已连接的调试设备时装好并打开；没有时说明原因，只给最短的安装和打开步骤；
   - 已经上线的交付包：直接打开线上地址（部署本身按第九节，全量发版先问用户）。
6. **测试账号与演示数据**：由施工队在交付包最后一期准备好，写进阶段交接的“试用准备”；包工头直接取用。只写本机演示账号，不写任何真实账号的口令。

### 3. 给用户的试用说明

唤起成功后立刻发给用户，紧跟在该期简报之后（简报的“需要您做的”写“按下方步骤试用”）：

```markdown
已为您打开：<页面 / 客户端名称>（<地址或打开方式>）
本次可试：<交付包名称>——<做完后能做什么，一句话>

测试步骤：
1. <做什么> → 应看到：<结果>
2. ……

注意事项：
- <测试账号与口令（仅本机演示）>
- <还是模拟 / 假数据的部分>
- <本包明确没做、容易被当成问题的>
- 有问题告诉我第几步、看到了什么（截图更好）；没问题回“通过”。
```

- **测试步骤不超过 7 步**，每步一行“做什么 → 应看到什么”；先走一遍主流程，最后 1–2 步测最关键的出错或边界情况。原型期按“请用户测试的路径”表覆盖空状态、加载中和失败提示，可以多于 7 步，但每步仍只写一行。
- **注意事项不超过 4 条**，只写会影响用户判断“对不对”的事：测试账号、哪些还是模拟的、本包没做的、怎么反馈。没有就少写，不凑数。
- 用业务话写，不出现命令和代码术语；启动、关闭都是包工头的事，不写给用户。
- 以期次文档里的试用说明为底稿，按施工汇报里的实际结果校正（入口变了、按钮改名了、某项挪到了下一个交付包），不照抄过时的草稿。
- 原型期额外写请用户重点看的几点和包工头的建议。

### 4. 等用户反馈

- 唤起后**等用户反馈再开下一个交付包**，等待期间不派新的施工任务。依据：用户 2026-10-03 确认——试用发现的问题可能改变下一个交付包的做法，先等反馈能避免返工。
- 用户回“通过”：交付包状态改为“已可用”，再开下一个交付包。
- 用户报了问题：
  - 小问题（文案、样式、个别按钮、不影响走通主流程的）：派施工队修，修完**不重新唤起**，交付包直接标“已可用”并开下一个交付包，修好的点写进下一次试用说明让用户顺带看一眼；
  - 主流程走不通或结果明显不对：修完重新唤起，只给复看要走的步骤；
  - 改变业务规则或已确认决定的：先按第六节处理。
- 原型期例外：放行条件要求修改项经用户复看，所以原型期的修改项全部改完后**统一唤起一次**复看，不改一项唤起一次。
- 用户测完不需要再看时，关掉包工头启动的试用程序。

### 5. 原型期的额外规则

- 有依赖的原型期（例如期 2 在期 1 界面上继续做）必须等前一期确认、修改闭环后再派，不能因为前一期“代码做完了”就派。依据：第一轮包工头一度计划期 1 做完就派期 2，对照文档后更正。
- 原型期的完成标签等用户确认后再打。
- 门槛线之前的期次全部确认后，派一个子 agent 按用户确认结论复核门槛线之后的期次，结论分为“无实质变更 / 已更新 / 作废重拆”，复核完才放行后端施工。

## 六、处理用户的答复与决定

- **原话转交**：用户的答复原样转给负责的子 agent，由它记进需求证据（编号接续），并改掉受影响的决策和所有受影响的期次文档。
- **答复含糊**（“好像是”“应该可以”）：不猜，能用代码或文档核实的先核实，再按核实结果处理，并告诉用户。
- **没有逐条回复**：用户用一句话概括回复了多条建议时（如“确认了效果，目前定稿”），写明“我理解为 X、Y、Z 都同意，已按此记录，不是这个意思请告诉我”。
- **用户没看懂某一题**：不急的题先按包工头建议的默认值施工，不阻塞，在《待您决定》里移到“待追认”，换成具体场景再解释一次；卡住施工的题不按默认，换个具体场景重新问（第十节“待您决定”）。
- **拆两段派**：需要用户先拍板（删除清单、规则缺口、口径选择）的期次，第一段子 agent 只读，产出清单写进状态文件；包工头把清单翻成业务话交用户；确认后续派同一个子 agent 施工。依据：一期清理任务只读核对约 7 分钟，确认后续派施工约 20 分钟，没有返工。
- **答复改变了已确认的决定**：先更新决策台账，再续派；用一道带数字的确认题锁定口径（第十节）。

## 七、并行

承诺并行之前，对照两期文档的“核心代码入口”和“任务清单”，确认没有同层、同文件的改动。

**可以并行**：

- 一方只改前端 / 客户端，另一方只改后端 / 服务端；
- 一方只读（核对、审查、排查），另一方施工，且读的不是对方正在改的文件。依据：只读核对与联调同时跑，整轮省约 7 分钟。

**不能并行**：两期改到同一层的同一批文件，或都要改数据库结构。依据：两期都要改同一个客户端接口文件，同时改会让一方编译失败；改为先后执行，额度不变，多花约 20 分钟。

**并行时的规则**：

- 任务书写明各自的目录地盘，提交时只列自己地盘内的路径；新文件先 `git add -- <具体路径>`。
- 需求证据、主需求文档、README 总览这类共用文档，同一时间只指定一方写；README 状态由包工头在两边都完成后统一更新。
- 推送冲突时先 `git pull --rebase`，不强推。
- 端口按用途分开：用户走查、子 agent 联调、子 agent 自测各用各的端口（写进项目档案）；不结束别人的进程。
- 一方需要另一方的干净代码时，用 `git worktree add` 从对应标签建副本，换端口运行。
- 客户端期与服务端期并行时，客户端只能对着模拟后端测；这一组结束后补一次真实联调。依据：两次补联调都挖出了只对模拟测试时发现不了的问题。

## 八、独立审查与仲裁

### 必审

- 涉及钱的期次（下单、支付、退款、扣费、额度、席位）做完后，派监理独立审查。依据：先后两次审查各挖出 1 个高危问题——升档少收钱、撤销非最近一笔续费会白送席位——施工队的测试都没覆盖，其中一条测试甚至把攻击场景当成正常用例。
- 鉴权、密钥、删除、数据迁移相关期次按风险决定，写进 README 的施工基线。
- 会动生产环境的脚本，执行之前先做语法解析校验，再派监理审查。依据：部署脚本连续三次因隐藏字符失败，校验加审查后一次成功。

### 仲裁

用户或包工头怀疑子 agent 结论有误时，派监理只读复核，把结论如实告诉用户，不迁就任何一方。依据：一次用户认为施工队“没仔细看、误报了”，复核后证明子 agent 是对的。

### 做法

- 施工队在汇报里附“供审查的重点文件清单”，审查任务书直接引用，审查通常约 5 分钟。
- 审查只读；任务书写明只读源代码，不打开配置、证书和密钥文件。
- 结论要求带“文件:行号”和触发场景。
- **意见分两级**：
  - **阻断**：有具体触发步骤、会造成真实业务事故（钱算错、越权、数据丢失或串号、用户主流程走不通），必须修完才算本期完成。
  - **记录**：理论极端情况、完备性、代码风格、“最好也证明一下”之类，写进“已知限制 / 技术待办”，不阻断交付、不新开期。
  - 监理意见不能直接变成新子期；确实需要新增工作的，由包工头按第四节第 5 条和第十五节判断。依据：一个团队后台项目里，监理每轮提出的新边界都被拆成新子期，期次越拆越细、业务始终没有交付。
- 发现问题后另派施工队修：先写测试复现，再修复；修复期间用户又定了新口径的，续派同一个子 agent 接着做。
- 审查可以和下一期并行，前提是下一期不改被审查的代码；修复等被审代码无人在改时再派。

## 九、线上操作、凭据与工具拦截

### 谁来做

- **默认由 AI 直接做完**：部署、服务器配置、管理后台录入、复用已有配置。不要把命令和表单甩给用户自己执行。依据：用户是产品岗，多次表示“不要让我自己去填”“之前这些你都可以直接运行，现在怎么都要我去终端运行”。
- 需要凭据或会改生产的操作，由**包工头亲自执行**，不派子 agent；子 agent 只做本机准备、只读排查和整理清单。
- **仍要先问用户**（项目档案可增减）：
  1. 对全部用户生效、不能撤回的操作（全量发版、公开发布）；
  2. 花钱或产生外部副作用的操作（真实付款、真实短信，测试金额也算）；
  3. 动与其他业务共用的基础设施；
  4. 不可撤回的删除（远程分支 / 标签、强推、清空数据）。
- 用户指定自己做的事按用户的来，例如“新服务商的 API Key 我自己在后台填，不要让我存文件给你读”。

### 凭据

- 复用已有配置里的密钥时，用脚本读出后直接写入目标（后台接口、服务器配置），值不打印、不进对话、不进文档、不进 Git。
- 聊天里出现过的口令（用户贴出、截图里露出），不转交、不使用，建议用户事后更换。
- 用户在开发调试期给出的管理员账号，只用于调接口录入与验证；口令不写进记忆、文档和任务书。

### 被工具拦下时

- 不换说法、不拆步骤、不借别的工具或别的 AI 绕过。
- 首选：请用户把会话切到“确认模式”，包工头发起命令，用户在弹窗里点允许；这一步做完请用户切回自动模式，因为后台子 agent 在确认模式下可能卡在等待批准。
- 需要长期放行时，权限规则由用户自己改；AI 不设计放宽自己权限的规则，也不改工具自身的权限设置。Claude Code 的放行规则按命令原文匹配：放行过的命令要单独一行、原样执行，前面不拼接 `cd` 等其他命令，否则仍会被拦。
- 只有在以上都不可行时，才把命令交给用户执行。交出前包工头逐行核对，写清每一步应该看到什么、异常时怎么办。依据：一次把子 agent 报的工具菜单编号原样转给用户，编号是错的，幸好用户执行前发现了。

### 部署安全

- 从干净的副本或标签部署，不要把别的期次做到一半的代码带上线。
- 改数据结构前自动备份；改服务器配置前先备份原文件。
- 部署失败先派子 agent 只读排查：线上现状、原因、修复方案。查清后报给用户，同意再动。
- AI 在服务器上操作期间，请用户不要同时在管理面板里改同一处。依据：用户在面板里手动建库、AI 也在建库，差点撞车。

## 十、和用户沟通

- **结论先行**：先说结论和对用户的影响，再说原因；推测要标“推测，未核实”。
- **业务语言**：先用具体场景讲清“现在是什么样”，再问要不要改。依据：“席位轮换”“立即重启更新”两次说得太抽象，用户没看懂，来回多问了一轮。
- **规则缺口先讲现状**：规则缺口背后往往是对现有机制理解不一致，先用例子讲清现在怎么算，再给选项和推荐。
- **用数字锁口径**：用户的回答改变了已确认决定时，用一道带数字的确认题锁定，例如“5 个席位、每席 100 点、只有 1 个人在用，最多能用多少点”。
- **问题编号、附建议**：需要拍板的事编号列出，每项给选项的业务后果和包工头的建议；不急的标明“什么时候之前回复就行”。
- **分出“不需要您操心的”**：子 agent 自行处理且有依据的事，单列一段告诉用户为什么不用管，避免用户被细节淹没。
- **不迁就**：复核证明子 agent 是对的，就如实说；用户的判断有误也直说，并给证据。
- **称呼与语言**按项目档案的沟通约定。

### 待您决定：不让要拍板的事被动态顶走

施工期间对话里不断有新动态，要用户拍板的事一旦只出现一次，就会被顶上去；之后再问时，包工头凭记忆重新概括，每问一次就简化一次。所以待决定事项要有固定存放位置和固定原文。依据：用户反馈“确认的内容被动态顶走，容易遗漏；AI 虽然多次询问，但每次都会简化”。

1. **登记进文件**：每个要用户拍板的事，按 `references/pending-decisions-template.md` 登记进 `docs/<功能名称>/待您决定.md`，带固定编号 `Q-xxx`。第一次就写完整：具体例子、选项后果、建议、最晚答复时间。以后每次提问都从文件**原样复制**，不重新概括。
2. **分两类**：
   - **卡住施工**：不答就不能继续的，以及涉及钱、不可撤回、推翻已确认决定、第九节“先问用户”的事。
   - **不急**：有建议默认值、晚点答也不卡施工的事，写明最晚哪一期开工前要答。
3. **卡住施工的事，用打断式提醒**：Claude Code 下用弹窗提问工具（AskUserQuestion），一次最多 4 题，按轻重排；同时用推送通知工具（PushNotification）发一句提醒，例如“包工头：有 1 件事要您拍板，期 5 在等”。弹窗挡在界面上，不会被动态顶走；弹窗期间后台子 agent 照常运行，它们的汇报等用户答完再处理。工具不支持弹窗或推送时（例如 Codex 下未核实），退回第 4 条的底部区块，并在简报第一行写“有事卡住，等您拍板”。
4. **每次停下都在消息最后放“待您决定”区块**：只要文件里还有未答或待追认的事，包工头每次停下来的那条消息，最后一段固定是这个区块，内容从文件原样复制。用户最先看到的永远是最底下的那条消息。没有待决定事项时不放。

   ```markdown
   ---
   **待您决定（共 n 项，按编号回复即可）**
   - Q-003【卡住施工，期 5 在等】<问题>？建议：A，<理由一句>。
   - Q-005【不急，期 7 开工前】<问题>？建议：B。到期未答将按 B 执行。
   - Q-002【已按默认执行，待追认】<问题>：当前按 B 做的，不同意请告诉我。
   完整背景见 `docs/<功能名称>/待您决定.md`
   ```

5. **不急的事攒着问**：不弹窗、不推送；新增时在当条简报的区块里出现，再集中到交付包完工唤起试用时一起问（第五节），减少打断。
6. **到期未答按默认执行**：不急的事到了最晚答复那一期还没答，按建议默认值施工，移到文件“已按默认执行、待追认”，记进当前决策台账，状态写“临时决定，待用户追认”；它继续挂在底部区块里，直到用户追认或改口。用户事后不同意，按第六节“答复改变了已确认的决定”处理。**卡住施工的事永远不按默认执行。**依据：用户 2026-10-04 确认。
7. **少播报过程**：子 agent 施工期间不发过程动态，只在收到汇报时发简报；动态越少，要拍板的事越不容易被顶走。
8. **答复后销账**：用户按编号回复后，原话记进需求证据，本项移到“已决定”并写明落地位置；用户一句话概括回复多项时，按第六节写明“我理解为……”。

### 简报

每期收尾的简报（不超过 10 行；有待决定事项时，后面紧跟“待您决定”区块）：

```markdown
期 N《名称》完成 / 阻塞
- 交付包进度：<交付包名称>，本包 x / y 期；全部交付包 a / b 已可用
- 做成了什么：<业务话，一两句>
- 需要您做的：<实测的页面 / 要提供的材料；要拍板的问题放在最后的“待您决定”区块；没有写“无”>
- 遗留：<待实测、待补录屏等；没有写“无”>
- 下一步：<期 N+1 名称，或等您答复>
```

多期同时进行时附进度表，按交付包列：

```markdown
| 交付包 | 用户能用上什么 | 状态 |
|---|---|---|
| 原型确认 | 看到并点完全部页面 | ✅ 已确认 |
| 网页登录与成员管理 | 主账号在真实网页登录、给成员分配模型 | 🔨 期 3 / 共 3 期 |
| 聊天记录查询 | 主账号查看成员聊天 | ⏸ 等上一个交付包 |
```

**进度不按期次数汇报**。“已验收 30 个单元”这类说法不能代替“用户能用上什么”；底层期次做了很多、交付包仍是 0 时，必须如实说“还没有能用的功能”，并检查是否命中第十五节熔断信号。

## 十一、叫停与恢复

- 用户说“停”时，所有子 agent 停在安全位置；向用户报告现场：每个子 agent 停在哪一步、有没有改动、有没有半截提交、仓库是否安全。
- 恢复时重新派活，任务书写明上次停下时留下的改动如何处理；不要接着用已停下的子 agent，以免它仍跑在旧设置上。

## 十二、轮次交接

包工头会话也会变长：每回一次话都要重读整段历史，越往后越费额度、越慢；对话过长时，工具会自动压缩早期内容，细节（某个决定是谁、什么时候定的）可能丢失。趁记忆完整时把要点写成文档，比事后靠压缩后的记忆可靠。

### 1. 什么时候交接

包工头要**主动提出**，不等用户问。出现以下任一信号时，向用户建议交接，说明理由：

- 本轮已连续派了约 8–10 次施工任务（拆出的子期、修订、返工都各算一次，不按期号算），或累积了大量截图、长日志；
- 工具已经自动压缩过一次对话，或提示上下文即将用完；
- 用户提出“上下文是不是太长了”“是不是该开新窗口了”；
- 用户要换电脑、换工具或暂停；
- 一个批次的停点到了。

用户同意后按下面的顺序收尾。用户希望继续做完手上这一期再交接的，先做完再交。

### 2. 交接前收尾

1. **正在做的期次收到安全点**：能做完的做完，提交、打标签；做不完的停在可恢复位置，提交已完成部分，填好该期文档的“阻塞快照”。
2. **还在运行的子 agent**：等它交回，或通知它停在安全点后再交回。不要留下仍在运行的子 agent——它的汇报只会回到旧窗口，新窗口收不到。
3. **临时状态文件转存**：子 agent 的状态文件放在本会话的临时目录，新窗口（尤其换电脑后）看不到。其中仍有用的内容（只读核对清单、排查结论、待用户确认的选项）抄进交接记录或对应期次文档，不要只留路径。
4. **更新期次总览**：README 状态列与实际一致，遗留项写清。
5. **试用程序**：有做完但还没交用户试用的交付包，先按第五节唤起再交接。旧窗口关闭后，它启动的试用程序可能随之停止；交接记录里写明哪个交付包还在等用户试用，新窗口接手后重新唤起。

### 3. 写交接记录

- 包工头亲自写，不交给子 agent：只有包工头手上的信息最全，转给子 agent 写反而要重述一遍。
- 写结论、不写流水：正文控制在约 150 行内，用业务语言；不写文件哈希、执行次数、逐次观察记录。下一任需要的技术细节以“在哪份阶段交接 / 哪个标签”引用。依据：一份长达 87KB 的施工流水和满篇哈希的交接，让新包工头开场就背上很重的上下文，用户也读不懂。
- 按 `foreman-handoff-template.md` 写，放在 `docs/<功能名称>/包工头工作记录-第N轮-期X至Y.md`。后一份只写本轮新增；前几份仍有效的部分在开头列出并用“见第 N 轮第 X 节”引用。
- 有中途停下的期次时，必须写“进行中的期次”一节：停在哪一步、改了哪些文件、提交到哪、恢复的第一步。
- 把用户在本轮定下的长期规则写进工具的长期记忆（如有），记忆里只放规则和交接记录的位置，不放细节；交接里写明哪些规则已经失效（例如用户取消了某项要求）。
- **提交并推送**交接记录（按项目保存策略）。新窗口、尤其换电脑后，是从仓库里读交接的。提交信息例如 `docs(<feature-slug>): foreman handoff after phases X-Y`。

### 4. 交给用户

最后一条消息直接告诉用户怎么开新窗口，不让用户去文档里找：

```markdown
本轮交接已写好并推送：<交接记录路径>

开新窗口时：
1. 用 <T1 系列，如 Opus / Astra> 开一个新会话<，建议等额度重置后再开>；
2. 粘贴下面这段：

<开场提示词全文>
```

有额度要求时，建议用户等额度重置后再开新包工头，让下一批次能用完整的额度窗口。

### 5. 交接后补记

写完交接后，用户在同一窗口又定了事、又让做了小改动的，在交接记录末尾追加“交接后补记”一节（内容、结果、提交），并据此更新第三节待办；补记后重新提交推送。开场提示词不变时无需重发；变了就把新版本再贴给用户。

### 6. 新窗口接手

新包工头读完开场提示词列出的文件后，先按第二节“开工准备”查现场、对文档，第一条回复给用户：

- 已读完哪些交接、当前进度（用期次状态表）；
- 发现的现场问题（陌生提交、本机环境缺什么、期次文档与现状不一致之处）；
- 交接第三节 A 类待决定事项，加上本批开工前要用户决定或提供的事，编号列出、附建议，请用户一次答复。

用户答复后再派活。依据：上线验收那一轮的新总指挥就是这样开场，一次问清 8 个问题，用户按编号答复后当场开工。

### 7. 意外中断时的恢复

窗口崩溃、来不及写交接、或对话被压缩到看不清前情时，新包工头按以下顺序重建现场，不依赖旧聊天：

1. 期次总览 README 的状态列：哪些期已完成、哪些有遗留；
2. 最近一份交接记录（若有）和各期文档末尾的“阶段交接记录”“阻塞快照”；
3. `git log`、阶段标签与 `git status`：最后完成到哪、有没有未提交的半截改动；
4. 需求证据与决策台账末尾：最近有哪些用户决定；
5. 仍无法确定的（例如某期做到一半、改动是否可用），列给用户确认后再动，不猜。

重建后先补写一份交接记录，再继续施工。

## 十三、不支持子 agent 时的退路

工具不能派子 agent，或用户要求手动执行时：

- 每期单独开一个窗口，把期次文档全文和本期任务书一起作为初始提示词；
- 用户临时充当包工头：开工判断、收尾核对、README 状态更新按本工作流第四节执行；
- 期次文档、阶段交接、检查点规则完全不变，随时可以切回包工头模式。

## 十四、施工纪律速查

写进每份开发任务书（模板已含）：

| 纪律 | 内容 | 依据 |
|---|---|---|
| 测试省着跑 | 开发中只跑与改动相关的测试；收尾全量只跑一次；失败只修失败项、只重跑失败项；不为“验证稳定性”反复重跑；项目另有规定的按项目（如界面调整阶段由用户自测，不跑自动测试） | 用户原话“不要让子 agent 去来回跑测试” |
| Git 安全 | 禁止 `git add .`、`git add -A`、`stash`、`reset`、`clean`、`restore`、`checkout --`；只提交指定路径；附注标签显式写提交号 | 防止混入用户改动；还原类操作被权限拦截过 |
| 不许猜 | 拿不准就停在可恢复状态，填阻塞快照，写进汇报 | 官方文档说不清的用量口径，按要求不猜，留给真实调用核对，避免错误计费 |
| 不碰凭据 | 子 agent 不读、不打印、不转交真实密钥；需要时写成清单交包工头 | 读密钥的任务书整体被安全规则拦下 |
| 汇报短 | 汇报不超过 300 字、大白话，同时写状态文件 | 汇报丢失 |
| 自加规则单列 | 文档没写、自己定的做法在汇报里单列，等用户拍板 | 多条自加规则需要用户确认 |
| 临时文件 | 临时构建目录放会话临时目录，用完即删；不在仓库外留目录 | 子 agent 删仓库外目录被权限拒绝，只能留给用户手删 |
| 测试副作用 | 测试会改写受版本管理的文件（如截图）时，子 agent 自己还原，或让测试写到忽略目录 | 冒烟测试反复改写文档里的确认截图 |
| 新增依赖要真启动 | 新增依赖注入等运行期才暴露的问题，在开发环境真启动一次 | 测试环境不校验，真启动才报错 |
| 防御相称 | 校验和边界只做真实数据量级、真实事故、用户要求、钱 / 权限攻击场景需要的；其余写“已知限制” | 为理论极端情况拆出大量子期，业务迟迟不交付 |
| 验证轻量 | 优先复用项目已有测试、编译和真机试用；不为每期自造一次性验证工具链，迁移和钱的必要核对除外 | 每期自建核对脚本和指纹比对，验证成本超过开发本身 |

## 十五、失控信号与熔断复盘

拆分和防御本身不会自己停下来：每次拆分都产生新文档，文档越多下一期上下文越重、评分越高，又触发新的拆分；监理每轮也总能找到新的理论边界。所以要有硬性的刹车点。

### 1. 熔断信号（任一出现即停止派新活）

- 同一原期需要第二次拆分（出现 `N b` 还要再拆的情况）；
- 一个交付包累计超过 4 期仍未交付；
- 连续 3 期做完，用户仍然什么新功能都用不上；
- 新增的期次只产出“准备 / 证明 / 审计 / 事实读取”，没有下游直接使用；
- 用户质疑进度或方向，例如“怎么还没解决”“怎么卡了这么多文档”“是不是过度设计 / 过度防御了”。

依据：一个团队后台项目三次被用户质疑（拆得太细、一直没解决、是不是过度防御），包工头每次都承认流程偏重，然后换个说法沿原路线继续，问题没有解决。用户的质疑本身就是熔断信号，不能当成“需要解释一下”。

### 2. 复盘怎么做

包工头亲自做，不派子 agent，先回到第一性原理：

1. **业务目标**：这个交付包到底要让用户用上什么？用一句大白话写出来。
2. **真实规模**：查实相关数据的真实量级（条数、单条大小、并发人数），不按理论最大值。
3. **已完成**：哪些已经能用、哪些只是中间产物。
4. **卡点**：为什么卡住——是业务本身难，还是防御、验证或方案过重？
5. **方案对比**：至少给出“简化方案”和“继续原方案”两个选项，各写剩余工作量（按期数估）、能防住的真实风险、放弃的部分写进“已知限制”后对用户的实际影响，并给出包工头的建议。

### 3. 交给用户

复盘结果用大白话、带具体例子交用户选择，例如：“旧话术迁移现在的方案还要约 6 期；简化方案是先备份旧文件、迁移后核对条数并抽查 20 条、出问题一键用备份恢复，约 1–2 期。简化方案不防的是单条超过 4MB 的话术，您现有数据里最长一条约 3 000 字。建议用简化方案。”

用户选定后：

- 把决定记进当前决策台账；
- 已完成的期次和标签保留，不删除历史；作废的期次在 README 总览标“已作废（被 D-xxx 替代）”，不再派；
- 按新方案重排剩余交付包，再开工。

### 4. 不要做的

- 不要在复盘后换个说法、沿原路线继续（例如把“子期”改叫“任务包”但内容不变）；
- 不要用“已验收 N 个单元”来回应用户对进度的质疑；
- 不要因为已经投入很多就继续原方案，已完成的工作只按它对剩余交付的实际价值计算。
