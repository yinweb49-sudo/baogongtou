# 分期开发提示词模板

用这个模板写 `开发提示词/README.md` 和 `期N-*.md`。目标是让每期能直接作为包工头派给施工队的任务书底稿（也能单独开窗口手动执行），AI 读完就知道要看什么、改哪里、不能碰哪里、怎么验收。包工头施工的流程见 `references/foreman-workflow.md`。

> **术语替换（先读）**：占位符 `{{前端}}`、`{{验收方式}}`、`{{结构检索工具}}`、`{{主库}}`、`{{次库}}`、`{{鉴权方案}}`、`{{白名单机制}}` 从**项目档案**取真实值替换；项目没有的机制就删掉对应句子，不硬套。
>
> **范围冻结（必做）**：期次只能拆自主需求文档“本次范围”中已准入的能力。模板出现的输入源、搜索、批量、第三方、体验或平台扩展只是条件说明，不代表要创建对应期次。
>
> **业务共识前置（必做）**：先读主需求文档“0. 业务需求共识”。存在“阻塞确认”时不得生成或执行正式实现期；只有用户知情且目标就是解除该阻塞的最小期 0 探针或备选视觉原型可以先行，并必须标为“解除阻塞期”。每期业务目标都必须能用大白话回指第 0 节最终期望效果。
>
> 注意区分两种“未确认”：**业务共识阻塞**是方向本身没定，方案写出来也没有基准，因此连文档都不生成；**视觉形态待确认**是方向已定、页面形态待验，文档照常一次写完，只拦施工。
>
> **证据与决策前置（必做）**：分期提示词是对主需求文档的二次压缩。生成正式实现期前确认当前决策台账没有阻塞，标准 / 审计模式的证据销账无“无归属”；解除阻塞期只承接它要验证的冲突编号，不扩展范围。每期写清承接的 `U/P/A/E/D` 编号。执行优先级为“当前有效决策 → 已确认最终效果与验收场景 → 主需求文档 → 本期提示词 → 原话证据”。
>
> **视觉先行前置（必做）**：从无到有且有界面时，完整读取 `references/visual-first-workflow.md`。**期 0 到期 N 的全部期次一次写完，不因等待用户确认而停笔**；改为在期次序列上划出视觉确认门槛线，门槛线之前是原型与前端可见效果，之后是后端、数据、鉴权、集成和迁移。期 1 文档必须写“本地预览与用户确认”：真实启动命令、预览入口、用户测试路径和放行条件。用户确认绑定具体版本、修改项闭环、门槛线之后的期次复核完成后，才开始后端施工。
>
> **AI 工作量前置（必做）**：生成分期文档前完整读取 `references/phase-workload-planning.md`。先列交付包（用户能用上的业务结果），再拆任务原子和依赖，对每期做六维评分与平衡；普通开发期控制在 4–7 分，8 分以上按“减负 → 换方案 → 拆一层”处理，只拆一层。分期边界服务于单窗口工作量、上下文负载、风险隔离和中断恢复，不要求每期都是完整业务功能，但每期必须属于一个交付包，单个交付包不超过 4 期。
>
> **Git 代码检查点前置（必做）**：生成分期文档前完整读取 `references/git-backup-workflow.md`。从项目档案读取保存策略；远程存在不等于用户授权推送。真实敏感信息一律阻止进入 Git，代码标签不能代替数据和外部状态回退。

## 开发提示词 README

```markdown
# <功能名称> · 分期开发提示词

本目录是“<功能名称>”的分期开发提示词，配合上级目录的《<功能名称>-开发需求文档.md》使用。

## 用法
- 默认由包工头施工（baogongtou 阶段二）：包工头按 `期N-*.md` 和下方“施工指挥基线”写任务书，派施工队执行，收汇报后更新本表状态。
- 手动方式：每期单独开一个开发窗口，把对应 `期N-*.md` 的全文作为初始提示词发给 AI。
- 每份提示词都限定核心必读材料、按需材料和一个主要问题，不要求新窗口重新加载全部项目历史。
- 执行者先读上一期“阶段交接记录”和代码恢复锚点（如有），再读本期核心材料；不得依赖旧窗口的聊天记忆。
- 按数字顺序开发；每期完成并验收通过后，再进入下一期。
- 遇到“视觉确认门槛线”时停下施工：先按门槛线所在期的“本地预览与用户确认”把页面交用户实际测试，确认通过、修改闭环并复核下方期次后，再继续。文档本身已经全部写完，等待期间无需重写需求。
- 按 README 的保存策略建立代码检查点；只有已授权远程分支时才要求推送和远程验证。

## 交付包总览
| 交付包 | 做完后谁在哪里能做什么 | 包含期次 | 用户验收路径 | 状态 |
|---|---|---|---|---|

> 交付包按纵向切片排序：门槛线之后第一个交付包是最短的真实端到端链路。状态只写业务话：未开始 / 施工中（x / y 期）/ 等用户试用 / 已可用。

## 期次总览
| 期 | 所属交付包 | 文档 | 要解决的独立问题 | 来源编号 | 工作量 | 上下文 | 依赖 | 独立产物 / 验收 | 代码恢复锚点 | 状态 |
|---|---|---|---|---|---:|---|---|---|---|---|

> 存在前端原型期时，在期 1 与下一期之间插入一行门槛线，让人一眼看出施工放行位置：
>
> `| — | — | — | **视觉确认门槛线：期1 本地预览确认通过、修改项闭环、下方期次复核完成后，才可开始下方施工** | — | — | — | — | — | — | — |`
>
> 状态列只写业务话（约 40 字内），不写文件哈希、执行次数和内部函数名。
>
> 门槛线之上是原型与前端可见效果，之下是后端、数据、鉴权、集成和迁移。**全部期次在同一次输出中写完；门槛线只拦施工，不拦文档。**

## 证据与决策基线
- 需求证据：轻量模式内嵌于主文档 / 标准或审计模式见 `docs/<功能名称>/00-需求证据与原话参考.md`
- 需求证据销账状态：无归属条目 0 条（YYYY-MM-DD 核对）
- 当前决策台账版本：<版本 / 日期>
- 当前有效决策：<D-001, D-002 ...>
- 高关注项处理：<U-014 → D-002，本次必须；U-027 → 待确认>
- 执行约定：当前有效决策优先；只有决策缺失、冲突或证据不足时才停下来确认，不让已被替代的旧原话覆盖新决定。

## 前端视觉确认基线
- 当前任务授权：只编写文档，不改产品代码 / 已获用户授权实际施工
- 是否需要前端原型期：需要（期1）/ 豁免
- 豁免依据（豁免时必填）：无用户可见界面 / 明确 BUG 且没有新增视觉结构或交互决策 / 完全复用已确认交互，理由：<具体事实>
- 是否需要期0技术探针：否 / 是，需核实 <阻塞视觉成立的技术事实>
- 视觉确认门槛线位置：期1 之后 / 期<N> 之后（多个前端可见期时写最后一个）
- 门槛线之前的期次：<期0, 期1 ...>
- 门槛线之后的期次：<期2 ... 期N>，状态为“方案已成型，待原型确认后复核”
- 原型承载页面与主链路：<本次要先给用户看的页面和关键流程>
- 本地预览启动命令：<项目档案 {{验收方式}} 的真实命令>
- 本地预览入口：<http://localhost:<端口>/<路径> 或桌面端 / 移动端实际打开方式>
- 模拟数据形态核对结论：<区分已有系统已核实 / 新功能待设计 / 未知；字段、数据量、响应时间、失败方式>
- 用户视觉确认状态：未开始 / 已确认（YYYY-MM-DD）/ 已确认但有修改项 / 用户要求重做
- 确认记录位置：`期1-<原型期名称>.md` 的“前端确认记录”
- 确认版本锚点：<提交号或版本标识 + 页面入口 + 截图 / 录屏路径>
- 门槛线之后期次的复核结论：未复核 / 无实质变更，原样执行 / 已更新 <期次> / 已作废重拆 <期次>
- 后端施工放行条件：用户在本地预览确认通过、修改项闭环、版本锚点完整、门槛线之后期次已复核；未满足时不得启动数据结构、正式接口与鉴权改动。

> **文档不等确认。** 全部期次在同一次输出中写完，门槛线之后的期次照常写清任务、数据模型、接口和验收，只是标注“待视觉确认复核”。不允许只交付前端期就停笔，把剩余需求留到确认之后再写。
>
> 用户在确认环节说的新话追加到《需求证据与原始描述参考》，同步更新当前决策台账、主需求文档 §0.4 和 §4，并据此复核门槛线之后的期次；不得只留在聊天里。

## 全局约束（每期都适用）
- 当前有效的 `D-xxx` 是执行真相；原话负责举证，不得让已被替代的旧说法覆盖当前决定。
- 用户反复强调的点属于高关注信号，必须显式处理；是否本期实现以当前决策和范围为准。
- 用户明确否定过的内容不得实现，哪怕“顺手就能做”“做了更完整”。
- 第 0 节出现新的修改或冲突时，先更新并重新确认主需求文档，再继续开发，不按旧提示词自行猜测。
- UI 沿用项目现有设计语言。
- 存在前端原型期时，未取得绑定具体版本的用户确认并完成期次复核前，不执行正式建表、接口、鉴权和迁移期的施工；这些期次的文档照常一次写完，标注“待视觉确认复核”。期 0 只核实阻塞视觉成立的事实，不建设正式底座。
- 不复制敏感密钥或连接串。
- 风格、命名、目录结构与现有代码保持一致。
- 只实现主需求文档已准入且分配给本期的能力；不得顺手增加功能、管理入口、配置项、数据记录或后续扩展。
- 发现范围外优化时不要实现，最多在交付说明中标为“可选建议（不纳入本期）”。
- 每期只解决一个主要问题。实际影响面、任务包或阅读材料超过评估时，先减负、换方案，仍超标才停在可验证边界拆一层，不强行在当前窗口做完；需要第二次拆分时停下交包工头复盘。
- 防御、校验和边界测试只做真实数据量级、真实事故、用户明确要求、钱 / 权限攻击场景需要的部分；其余极端情况写进“已知限制”，不实现。
- 每期完成后填写本期文档的“阶段交接记录”；下一期从持久化代码、文档和代码恢复锚点（如有）恢复上下文。
- 涉及本地运行时，优先用项目约定的验收方式（{{验收方式}}）真机 / 真环境验证。
- 每期开始记录版本基线：Git 可用时记录起点提交和工作区；Git 不可用时记录目标文件清单与 SHA-256，并明确当前没有自动代码恢复锚点。用户原有改动不得覆盖、丢弃或混入本期保存范围。
- 每期验收通过后按保存策略完成敏感信息检查和代码检查点；只有已授权远程才推送。真实敏感信息不得进入 Git。
```

## 单期提示词结构

每份 `期N-*.md` 按下面结构写：

```markdown
# 期N 开发提示词 · <期次名称>

你是本项目的开发工程师。本期只解决：<一个独立问题>。<明确不做什么、依赖什么、完成后给下一期留下什么>。

## 本期业务目标（大白话）
<不用开发术语说明：本期完成后，谁可以在哪里做什么，会看到或得到什么结果；对应主需求文档 §0 的哪一项最终效果。>

- 所属交付包：<交付包名称>（本包第 x / y 期）
- 做完本期后离交付还差什么：<业务话；本期就是最后一期时写“本期完成后用户即可按交付包验收路径试用”>

## 本期要解决的独立问题
- 问题：<只写一个主要问题>
- 为什么现在解决：<它与前后期的依赖关系>
- 独立产物：<代码、契约、调研结论、迁移结果或测试证据>
- 完成后如何验证：<本期独立完成标准>

## 范围依据
- 明确需求：<对应主需求文档范围表中的条目>（来源编号：U-xxx / D-xxx）
- 必要配套：<如有，说明缺少它会阻断哪条主链路；没有则写“无”>（服务于：D-xxx）
- 当前有效决策：<D-xxx>
- 代码 / 外部事实：<E-xxx，如有>
- 本期承接的用户原话：
  > 【U-014】<原话原样引用，不改写>
  > 【U-027】<原话原样引用；属于高关注信号，按当前 D-xxx 结论处理>
- 本期不做：<列出容易被误加、但未准入或属于其他期次的内容>

> 实现时先执行当前有效决策。只有决策台账缺失、互相矛盾或无法解释验收场景时，才回查原话证据并停下来确认。
```

## 期次拆分方法

正式实现期先确认主需求文档第 0 节不存在“阻塞确认”，再按范围准入过滤，最后按 `references/phase-workload-planning.md` 拆任务原子、画依赖、评分和平衡。存在阻塞时只允许生成专门解除该阻塞、且用户已知情的最小期 0 探针或备选视觉原型；它不得夹带正式底座或其他需求。

- 分期首先服务于 AI 单窗口执行，不要求每期都是完整业务功能。
- 先列交付包并排纵向切片顺序，每期归属一个交付包，单包不超过 4 期。
- 普通开发期建议控制在 4–7 分；8 分以上按“减负 → 换方案 → 拆一层”处理，0–3 分轻量期原则上合并或写明独立检查点理由。
- 从无到有且有界面时，期 0 到期 N 一次写完，并在期 1 之后划出视觉确认门槛线；门槛线之后的期次标注“待视觉确认复核”，用户确认并完成复核后才开始施工，不得只交付前端期就停笔。
- 同一业务能力可以拆成多个关联技术问题（受交付包上限约束，只产出准备 / 证明 / 审计的期次不单独成期）；不要为省事按前端 / 后端 / 数据库机械拆（前端原型期是为消除视觉不确定性设立的风险隔离期，不算机械切块），也不要把调研、大量实现、迁移和清理塞进同一期。
- 每期只有一个主要问题、3–6 个核心任务包，并留下可验证产物和阶段交接。
- Git 检查和本地代码检查点按保存策略执行；远程推送只在已授权时进行，不创建“Git 备份期”。
- 只有需求已确认删除旧体系时才单独创建清理期，并放在新链路稳定之后。
- 体验、更多输入源、识别、搜索、第三方、批量、横向平台等只有在主需求文档已准入时才能成为期次。
- 不创建“以后也许会做”的占位期；可选建议不进入期次总览。

- 验收是“证据和决策足以让下一期不依赖旧聊天继续”，不是提交大量代码。

### 数据地基期（涉及数据变更时）

- 写本期实际涉及的实体、数据上下文、建表脚本、索引、可空字段和用户隔离。
- 只有本期确实需要对外提供数据能力时才写 Controller、Service 和 API 封装。
- 涉及持久化时验收“重启后数据不丢”；涉及多用户数据时验收“换账号只看自己的数据”。

### 云端或第三方期（已确认涉及时）

- 写密钥只在云端 / 服务端。
- 本期存在跨层调用时，写调用方经现有鉴权通道（`{{鉴权方案}}`）访问。
- 按实际链路写同步 / 异步和失败状态，不为模板新增异步机制。
- 写接口调研结论；未实测就写开发前需确认。

### 批量 / 搜索期（已确认涉及时）

- 只有存在“先预览再选择”的已确认流程时，才写候选数据是否落库。
- 只有数据规模或接口约束确实需要时，才写分页 / 游标 / 去重 / 上限。
- 涉及批量处理时，写单条失败是否影响整批。
- 涉及候选外链时，复用项目已有打开方式。

### 清理旧体系期（已确认删除时）

- 先列“必须保留”。
- 再列“删除清单”，按后端、前端、表、脚本、文档分组。
- 要求用 {{结构检索工具}} / 搜索核对依赖，分批删、边删边编译。
- 验收必须包含新链路回归和旧引用全局搜索。

### 体验打磨期（已确认且需独立验收时）

- 只写范围表中已确认的体验项，按价值排序。
- 不引入新链路。
- 验收只覆盖本期实际改变的页面状态和交互，不顺带增加编辑、批量、筛选或分页。
