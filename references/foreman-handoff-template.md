# 包工头工作记录模板

每轮施工结束时写一份，放在 `docs/<功能名称>/包工头工作记录-第N轮-期X至Y.md`。两个用途：让下一任包工头接手；让用户事后查证每个决定、每次事故的来龙去脉。何时交接、交接前怎么收尾、怎么交给用户、新窗口怎么接手，见 `foreman-workflow.md` 第十二节。

写作要求：

- 只做索引和汇总，细节以期次文档的阶段交接、需求证据、Git 历史为准。
- 后一份只写本轮新增；前几份仍有效的内容用“见第 N 轮第 X 节”引用，不重复抄写。
- 用户原话原样引用并写证据编号；不写口令、密钥等任何机密值。
- 用业务语言写，技术细节只在“技术待办”和“事故与教训”里出现；不写文件哈希、执行次数统计、内部函数名。
- 正文控制在约 150 行内：写结论，不写过程流水。技术证据以“见期 N 阶段交接 / 标签 X”引用。
- 不写临时目录里的文件路径让下一任去读：临时目录换窗口就看不到了，有用的内容直接抄进来。
- 写完提交并推送；之后有补充，追加到“交接后补记”。

````markdown
# <功能名称> · 包工头工作记录（第 N 轮：期 X–Y）

> 用途：① 供下一任包工头接手；② 供用户事后查证。
> 时间：YYYY-MM-DD HH:mm 至 YYYY-MM-DD HH:mm。
> 分工：包工头 <T1 系列>；施工队 <T2 系列> 子 agent <个数> 个；监理 <T1 系列>，本轮用过 <次数> 次。Codex 下写明角色文件填的具体型号。
> 工具：<Claude Code / Codex>，<电脑 / 仓库根路径>。
> 仍然有效的前序交接：<第 1 轮（事故教训、指挥方法）……；首轮写“无”>。

## 一、本轮结果一览

| 交付包 | 用户能用上什么 | 状态 |
|---|---|---|

| 期 | 所属交付包 | 内容 | 状态 | 关键标签 |
|---|---|---|---|---|

**现状（重要）**：<线上 / 生产跑的是哪个版本；哪些功能只在开发开关下生效；哪些还没部署>

**等用户试用的交付包**：<哪个交付包已做完、还在等用户试用反馈；新窗口接手后需重新唤起试用程序。没有写“无”>

**本轮线上操作**：<部署、配置录入、服务器改动：谁执行、备份位置、结果；没有写“无”>

### 进行中的期次（中途交接时必写，没有写“无”）

| 期 | 停在哪一步 | 已改动 / 已提交 | 恢复的第一步 |
|---|---|---|---|

### 转存的临时结论（没有写“无”）

<子 agent 状态文件里仍有用的内容：只读核对清单、排查结论、待用户确认的选项。直接写内容，不写临时路径>

## 二、用户在本轮的决定

| 证据编号 | 用户的决定（原话或摘要） | 落地位置 |
|---|---|---|

## 三、待办清单（下一任必须接住）

### A. 等用户决定
<见 `docs/<功能名称>/待您决定.md`：列出未答和待追认的编号与一句话问题，不重抄背景；没有写“当前没有等待用户答复的事项”>

### B. 等用户实测 / 提供材料 / 用户指定自己做的事
<要实测的页面、要补的录屏、要用户提供的材料；用户指定自己做的操作>

### C. 技术待办
| # | 事项 | 建议放在哪期 |
|---|---|---|

## 四、本轮事故与教训

<每条写：经过 → 原因 → 处理 → 教训。被工具权限拦截的操作单独列表：操作 / 拦截理由 / 改由谁执行>

## 五、指挥方法（本轮补充）

**本轮生效 / 失效的长期规则**：<用户新定的长期要求、用户取消的旧要求（如“不再询问额度”）；已写进长期记忆的注明>

<只写本轮新发现、可复用的做法；通用的已在 skill 的 foreman-workflow 里，不重复>

**额度与耗时参考**：<各期子 agent 耗时；额度读数（如项目要求记录）>

**换电脑须知**（下一轮可能换电脑时写）：<仓库路径差异、本机才有的东西（开发库、本机密钥、长期记忆、本机权限设置）、环境自检步骤>

## 六、后续计划

## 七、新包工头开场提示词（用户开新窗口时粘贴）

```
````
