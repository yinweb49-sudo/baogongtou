# 角色分级与工具适配

总指挥施工把工作分给不同能力档位的模型。流程只认**角色**和**档位**；本文件只写**模型系列名**，不写版本号。版本号会随模型升级变化，写死了，升级后会找不到对应型号、施工卡住。具体用哪一代，在开工时按工具当前可选的模型现场确定。

## 一、角色与档位

| 档位 | 能力定位 | 承担角色 |
|---|---|---|
| T1 前沿档 | 当前工具里最强、最贵的系列 | 总指挥、审查顾问 |
| T2 主力档 | 编码主力，性价比最高 | 开发 |
| T3 轻快档 | 便宜、快，推理较浅 | 轻量核对（可选） |

| 角色 | 做什么 | 不做什么 |
|---|---|---|
| **总指挥** | 和用户对话、写需求文档、规划批次、查实关键事实后写任务书、派活、收汇报、亲自执行需要凭据的线上操作、更新期次总览、写总指挥工作记录 | 不写产品代码、不重做验收、不替子 agent 跑测试 |
| **开发** | 按一期文档和任务书实现、跑必要测试、填写阶段交接、提交与打标签 | 不直接问用户、不碰真实凭据、不做本期范围外的事 |
| **审查顾问** | 只读：开发卡住或遇到不确定时给分析和指导；钱、鉴权、密钥、删除、迁移相关期次的独立审查；有争议结论的仲裁 | 不改代码、不打开密钥与配置文件 |
| **轻量核对** | 只读核对期次文档与代码现状是否一致、收集文件清单、查找引用 | 不改代码、不下结论性判断 |

为什么这样分：需求已经写清楚、拆成期次，开发阶段不需要大量设计和思考，主力档足够，而且额度消耗低得多；最强档留给规划、沟通、查实和审查这些需要判断的环节。

需求文档阶段由总指挥亲自完成，不派子 agent：需求需要与用户逐句对话、逐字归档原话、当场处理冲突，转手会丢信息。

轻量核对是可选角色。核对内容简单时，总指挥直接并入开发任务书的第一步，不额外派人。

## 二、适配对象与系列对照

本 skill 的施工部分适配两个支持子 agent 的开发工具：**Claude Code** 和 **OpenAI Codex**。只支持单会话、不能派子 agent 的工具仍可使用需求编写部分，施工退回“每期单独开窗口、手动粘贴期次文档”的方式（见 `commander-workflow.md` 第十三节）。

| 档位 | Claude Code | Codex |
|---|---|---|
| T1 前沿档（总指挥 / 审查顾问） | Opus | Astra |
| T2 主力档（开发） | Sonnet | Sol |
| T3 轻快档（轻量核对） | Haiku | Luna |

> 只列系列。某个系列在工具里暂时不可用时，先告诉用户，并说明可以选的替代（例如同档位的上一代），由用户决定，不要自行降档或升档。工具里出现了对照表没有的新系列，档位未经实际施工验证前不默认放进任何档位；用户指定时按用户的来，并记进项目档案。

## 三、Claude Code 用法

- **总指挥**：用户在 Opus 系列的会话里触发本 skill（`/model` 切换，或启动时指定）。
- **派子 agent**：用 Agent 工具，`model` 参数写系列别名：开发 `sonnet`、审查 `opus`、核对 `haiku`。别名会自动对应该系列当前最新一代，不需要写版本号。子 agent 类型用通用型即可，任务书写在 `prompt` 里。
- **别名不可用时**：通常是工具版本太旧，还不认识最新一代。请用户先升级 Claude Code，不要退回旧型号凑合。依据：第一轮开工时工具版本旧，主力档最新一代不可用，用户升级后恢复。
- **续派**：同一个子 agent 已有上下文时，用 SendMessage 按名字或编号续派，比新派省时（实测：用户补充决定后续派，14 分钟完成一项改动）。
- **后台运行**：子 agent 默认后台运行，完成后通知总指挥；总指挥不轮询、不提前臆测结果。
- **状态文件**：写在会话的 scratchpad 目录（系统提示里给出的临时目录），不写进仓库。
- **权限**：自动模式下有安全审查，会拦下生产部署、读取凭据、修改自身权限设置等操作；用户在聊天里口头同意，审查看不到、不认。处理方式见 `commander-workflow.md` 第九节。

## 四、Codex 用法

- **总指挥**：用 Astra 系列启动会话（启动参数指定，或会话中 `/model` 切换）。
- **角色文件**：Codex 通过“自定义 agent”文件给子 agent 指定模型。把本 skill 的 `templates/codex-agents/*.toml` 复制到项目的 `.codex/agents/`（团队共用、随仓库提交）或 `~/.codex/agents/`（个人跨项目）。每个文件定义一个角色：`name`、`description`、`developer_instructions` 必填，`model`、`model_reasoning_effort`、`sandbox_mode` 可选。
- **填型号**：Codex 角色文件里的 `model` 必须是工具认得的完整型号，只写系列名它不认。模板里的 `model` 是占位符，开工时总指挥：
  1. 列出 Codex 当前可选的模型（会话里 `/model` 可以看到）；
  2. 按系列名（Sol / Astra / Luna）挑最新一代，填进对应角色文件；
  3. 告诉用户填了哪个型号。找不到对应系列时停下问用户，不要自己换系列。
  模型升级后重复这三步即可，流程文档不用改。
- **没有角色文件时**，子 agent 会继承总指挥的模型——开发也会用 Astra，额度消耗明显变大。施工前必须先放好角色文件。
- **派子 agent**：总指挥在对话里按角色名派活（例如“派 `s2s_developer` 执行期 3，任务书如下”）。
- **思考档位**：开发用 `high`，审查用 `xhigh`，核对用 `medium`。不要给子 agent 设会自动再委派的最高档（如 `ultra`），否则层级失控。档位名称以 Codex 当前支持的为准。
- **并发上限**：由 `config.toml` 的 `[agents]` 段控制（如 `max_concurrent_threads_per_session`）；并行派活前确认上限够用。
- **子 agent 不能直接和用户对话**，结果回到总指挥；用户可在界面或 CLI 的 `/agent` 查看子 agent 线程。
- **状态文件**：写在仓库外的临时目录（由总指挥在任务书里指定绝对路径），不写进仓库。
- **续派**：当前 Codex 版本能对已有子 agent 追加指令时优先续派；不能时新派，并把上一轮状态文件路径写进新任务书。

## 五、两个工具的差异

| 差异 | Claude Code | Codex | 本 skill 的处理 |
|---|---|---|---|
| 子 agent 指定模型 | 派活时写系列别名 | 预先放好角色文件，开工时填当前最新型号 | 第三、四节 |
| 子 agent 权限 | 继承会话权限；自动模式下有安全审查拦截高风险操作 | 继承会话的沙箱与审批设置；会话若完全放开权限，子 agent 也完全放开 | “先问用户”的事项和凭据规则由 skill 自己守住，不依赖工具拦截（`commander-workflow.md` 第九节） |
| 聊天里的口头授权 | 安全审查看不到，被拦的仍会被拦 | 没有安全审查，口头授权后可以直接执行 | 都按第九节：先问清楚再做；被拦时请用户切确认模式点允许 |

Codex 不会替你拦，所以在 Codex 下更要严格执行第九节的“仍要先问用户”清单，以及“凭据不给子 agent”。

## 六、换代与覆盖

- 本文件只写系列名，模型换代时本文件不用改；Claude Code 的别名自动跟随最新一代，Codex 按第四节“填型号”三步更新角色文件。
- 工具新增或撤下某个系列时，才更新第二节对照表。
- 项目可以在项目档案的“总指挥施工”一节覆盖默认映射（例如某项目开发改用 T1），要写明理由。
- 用户在会话中临时指定模型时，以用户指定为准，并在总指挥工作记录里记一笔。
