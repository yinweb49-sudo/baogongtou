# 需求文档 / 开发提示词 / 包工头施工 评审清单

对照模板逐条核对，发现问题就指出位置和改法。带 `{{}}` 的术语按**项目档案**取值；项目没有的机制（多库 / 白名单 / 计费 / 云端层）对应条目跳过，不因缺失判为不合格。

## 需求证据与当前决策

- 已按轻量 / 标准 / 审计模式选择合适的证据强度，没有让小修复承担不必要的全量档案流程。
- 标准 / 审计模式存在独立的《需求证据与原始描述参考》，并在主需求文档之前产出。
- 抽查若干条原话，能在原始对话里一字不差地找到：没有改字、改标点、删句、合并同义句、把口语改成书面语、纠正错别字。
- 真实敏感信息已替换为 `[已脱敏：类型]`，没有因为逐字保真把密码、令牌、私钥、真实连接串或个人敏感信息写进仓库。
- 标准 / 审计模式没有删除与需求有关的重复、情绪化或已被推翻的原话；被推翻的原话仍在档案里作为演变证据。纯跑题内容可标“非需求上下文”，轻量模式只保留关键证据。
- 编号按对话时间顺序分配，没有重排、跳号或复用；分组只影响阅读顺序。
- AI 的发言只有在用户明确表过态时才记为 `A-xxx`，且写明了用户表态的原话编号；没有把 AI 的推测混进原话正文。
- 反复强调清单、明确否定清单单独成表，没有埋在正文里；重复被当作高关注信号，不是自动优先级。
- 当前决策台账使用 `D-xxx` 记录当前有效、待确认和已被替代状态；代码 / 外部事实使用 `E-xxx`，没有冒充用户原话。
- 执行优先级为“当前有效决策 → 已确认最终效果与验收场景 → 主需求文档 → 分期提示词 → 原话证据”，没有让过期原话覆盖新决定。
- 主需求文档的范围表、明确不做、当前决策、待确认问题都标注了来源编号；没有出现凑不出来源编号的条目。
- 用户反复强调的点在主需求文档里显式处理；纳入、后置或不做均有当前决策依据。
- 用户明确否定过的内容出现在“明确不做”，没有被重新加回范围。
- 需求证据销账表已回填，去向只使用“已写入 / 已明确不做 / 待确认 / 阻塞确认 / 非需求上下文”；非需求上下文有理由，未借此丢弃真实约束。
- 分期提示词写明了每期承接的原话编号；反复强调项在某一期里有明确落点，没有散落进“后续优化”。
- 技术限制只被写成实现约束，没有被用来改写或删掉用户诉求；确实做不到的写进了待确认并说明障碍。

### 开发过程中提需求（场景 B）追加核对

- 档案写明了触发场景；场景 B 有需求起点锚点，锚点位置和依据经用户确认，锚点之后按文档强度收录：审计模式保持完整，标准模式不漏需求相关内容，轻量模式不漏关键需求、否定和冲突。
- 前序相关内容是 AI 找全后交用户勾选决定的，不是 AI 自行判断收录；被排除的只留编号、位置和一句话摘要，没有留全文，也没有被彻底抹掉。
- 与已有需求档案完成对账：被本次影响的旧编号已列出并判定是补充 / 明确替换 / 冲突；冲突走了阻塞流程，没有自行以新盖旧。
- 档案归属正确：改同一功能已确认范围的追加到现有档案且编号接续，另起一件事的新建档案且双向交叉引用；没有为同一功能留下两套互相不知道的需求档案。
- 取不到原文的条目标了 `⚠ 摘要重述`，没有冒充原话；这类条目未进反复强调清单、未被当成已确认依据，销账去向为“待确认”。
- 用户对技术方案的表态（用哪个方案、先修哪个报错）没有被当成需求写进原话档案，而是写进了当前决策台账。
- 夹在调试语境里的原话逐字保留且标出了调试语境，没有被删掉，也没有被误读成需求。

## 业务共识与冲突

- 主需求文档标题后第一节就是“0. 业务需求共识”，没有被背景、架构或技术摘要挤到后面。
- 分别写清用户提出需求的原始目的、最初原始目标、AI 当前理解的最终期望效果；原始目标作为历史记录保留，未被最终方案覆盖。
- 全部使用普通业务语言，能让不了解开发的用户判断“谁使用、从哪里开始、做什么、最后得到什么”；没有用接口、表、字段、服务、队列等术语代替业务结果。
- 多轮沟通中的补充、明确替换和冲突有来源编号、有影响、有“已确认 / 待确认 / 阻塞确认”状态；只有一轮时明确写“暂无需求演变或冲突”，没有虚构历史。
- 原话之间存在矛盾时，两端原话被原样贴出并说明了各自的业务后果，交给用户选；AI 没有替用户选、没有同时保留两个分支假装兼容、没有用“综合考虑后按 X 处理”这类含糊表述掩盖分歧，也没有先做了再问。
- 用户没说过的原始目的、业务价值和最终效果未被 AI 擅自补写；技术限制未被当成产品目标。
- 最终期望效果与后续范围、交互、验收和期次一致；不存在前面说一种业务结果、后面按另一种结果开发。
- 会改变使用者、业务结果、主流程、权限、计费、数据归属、删除范围或系统边界的冲突未解决时，没有生成或执行正式实现期；只有用户知情且专门用于解除冲突的最小探针或备选视觉原型可以先行。

## 范围与过度设计

- 每个产品能力、技术改动、验收项和开发期次都能回指“明确需求”或“必要配套”；必要配套说明缺少它会阻断哪条主链路。
- 没有依据的入口、角色、配置、搜索、筛选、批量、更多输入源、分享、埋点、历史、调度、管理后台和平台扩展未进入本次范围。
- 可选建议与本次交付明确分开，未混入任务清单、数据 / 接口设计、验收标准或期次总览。
- 错误处理、兼容性、可访问性、测试和回归只覆盖本次直接触达的链路，没有借质量要求扩大产品能力或重构无关模块。
- 使用能完成目标的最小闭环；没有为了凑章节、凑期次或匹配模板示例而增加设计。

## 主需求文档
- 结构覆盖本次实际需要的内容；简单需求允许合并或删除不适用章节，不以 11 节齐全为目标。
- 元信息标明业务确认状态与当前任务授权；第 0 节明确区分“文档已写全，可进入原型施工 / 视觉已确认且后续期次已复核，可升 v1.0 / 业务方向仍然阻塞”。
- 有“本次范围与依据”和“明确不做”；范围内每项标明“明确需求 / 必要配套”及依据。
- 当前决策台账每条有状态、来源、理由、日期和替代关系；已确认与待确认分开，未验证的不写成当前有效结论。
- 存在关键假设表，写清证据、假设错误的影响、验证时机与状态。
- 存在适合项目规模的成功信号；没有为了填模板编造企业 KPI。
- 核心功能使用“前提—操作—可观察结果—证明材料”的场景化验收。
- 架构只展开本次触达的层；涉及密钥时写清归属，密钥不下发到不该有的层。
- 涉及数据变更时，数据模型写清用户隔离与加列 / 建表方式（按 `{{主库}}` / `{{次库}}` 的实际约定）；不涉及时没有新造表或字段。
- 涉及接口变更时，写清鉴权方案（`{{鉴权方案}}`）、白名单（`{{白名单机制}}`，如有）、是否计费；不涉及时没有为实现方便额外新增接口。
- 分期计划包含六维工作量评分、平衡结论和拆分 / 合并理由，没有只按业务模块列期次。
- 有前端原型期时，期次总览标出了视觉确认门槛线，且门槛线之后的期次内容写全，没有只写到期 1 就停笔。

## 开发提示词
- 一期一文件；每期含大白话业务目标 / 独立问题 / 范围依据 / 工作量评估 / 上下文边界 / 前置状态 / 阻塞点 / 任务清单 / 约束 / 验收 / 阶段交接，数据模型只在实际涉及时展开。
- 门槛线所在期额外含“本地预览与用户确认”和“前端确认记录”；其阶段交接写了本地预览是否已交用户实测、确认结论、修改闭环状态和后续期次复核结论。
- 每期先读主需求文档第 0 节，业务目标能回指已确认的最终期望效果，没有按过期或冲突版本施工。
- 每期都有范围依据，内容完全来自主需求文档已准入范围；没有可选建议、占位期或“顺手做”的功能。
- 每期能独立验收；“重启不丢、按用户隔离”等只在本期实际涉及持久化或用户数据时要求，且明确本期不做什么。
- 引用的需求文档与代码模板路径真实存在。

## 视觉先行与前端原型期

- 已完整读取 `references/visual-first-workflow.md`。
- 从无到有或明显改变用户流程且有界面时，期1 是前端原型期；这是需求发现门槛，不是可选优化。
- 豁免依据只来自无界面、明确 BUG 且没有新增视觉结构或交互决策、完全复用已确认交互，并给出具体事实；目标明确的文案纠错不会因像素变化被误判为必须原型。
- 技术可行性会阻塞原型成立时先安排最小期0探针；探针后仍回到原型，没有借探针直接建设正式底座。
- 期 0 到期 N 一次写完，没有因为“等用户确认视觉”只交付前端期就停笔，把剩余需求留到确认之后再写。
- 未经视觉验证的章节和期次标注了“待视觉确认复核”并写清会如何改变，既没有写成“已确认方案”，也没有留白、写“待补充”。
- 期次总览有显式的视觉确认门槛线：门槛线之前是原型与前端可见效果，之后是后端、数据、鉴权、集成和迁移；门槛线之后没有再按“接口期 / 数据库期 / 联调期”机械切块。
- 原型期文档写了“本地预览与用户确认”：真实启动命令（不是“启动开发服务器”这类空话）、预览入口地址、请用户走的测试路径表、放行条件。
- 用户测试路径覆盖正常有数据、空状态、加载中、失败提示和关键动作，不是只给一个地址让用户自己找。
- 用户只要求编写 / 评审文档时，把全部期次和确认门槛写完整，没有擅自修改产品代码；实际施工时能指出用户授权依据。
- 原型期要求写在项目正式前端目录、沿用现有组件与设计语言、模拟数据做成可整体替换的数据层；全新项目使用预期投入生产的技术栈创建最小正式脚手架，没有用临时静态页、截图稿或外部原型工具产物冒充产物。
- 原型期明确不建表、不写正式接口、不接鉴权、不做数据迁移；模拟数据层没有进入生产链路。
- 模拟数据形态区分“已有系统已核实 / 新功能待设计 / 未知”，并覆盖关键字段、数据量、响应时间和失败方式；看不清的项标注“数据形态未核实”。
- mock 和调试入口通过开发环境开关或等价机制与生产隔离，生产构建验收确认无 mock 引用。
- 原型演示覆盖正常有数据、空状态、加载中、失败提示和关键动作跳转，不是只摆一个填满假数据的完美页面。
- 原型期《前端确认记录》包含提交号或可复现的非 Git 版本锚点、页面入口、截图 / 录屏、确认项、修改项、否定项和未核实项；非 Git 锚点包含不可覆盖标识、文件清单哈希和运行命令。
- 门槛线之后涉及数据结构、正式接口或鉴权的期次，前置状态写明依赖视觉确认已通过、修改项已闭环，并留了复核结论的填写位置；没有出现未确认就开工后端底座。
- 用户在确认环节说的新话已追加证据并更新当前决策，主需求文档 §0.4 和 §4 已同步；确认结论没有只停留在聊天里。
- 确认后已逐条复核门槛线之后的期次，结论写成“无实质变更原样执行 / 已更新哪几期 / 已作废重拆哪几期”，没有跳过复核直接施工。
- 原型期评分未因“一次看全所有页面”而超过 7 分；超了的已按页面或主链路继续拆。

## AI 工作量与上下文

- 分期被定义为 AI 单窗口执行单元，优先按工作量、上下文、风险和依赖拆分，没有要求每期都形成完整用户可见功能。
- 先列任务原子和单向依赖，再组成期次；没有先按业务菜单、前端 / 后端 / 数据库命名后硬塞任务。两种情况不判为机械切块：为消除视觉不确定性设立的前端原型期（应排在实现期施工之前），以及由视觉确认门槛线划出的“门槛前 / 门槛后”边界（线上有真实的用户确认动作）。
- 每期对变更面、跨层依赖、不确定性、数据 / 安全风险、验收复杂度、上下文负载逐项给出 0–2 分和可验证依据。
- 评分覆盖读材料、理解业务、实现、验收、交接与备份的整期负担，没有只按代码量判断。
- 普通开发期总分为 4–7；8 分以上已强制拆分。多期中的 0–3 分轻量期已合并，或明确说明其作为调研确认、迁移、清理或高风险检查点的独立价值。
- 普通开发期最高分与最低分相差不超过 3；没有一期承担绝大多数开发、后续期次只剩零碎补丁。
- 每期只解决一个主要问题，普通期有 3–6 个核心任务包；没有把调研、大量实现、数据迁移和旧代码清理塞进同一期。
- 不确定性为 2 时先调研 / 确认，产出现状证据、已确认决策和后续入口；没有在关键结论未确认时直接编码。因“界面形态未经用户视觉确认”记 2 分的，已先安排前端原型期，确认通过后才降分。
- 数据 / 安全 / 可逆性风险为 2 时已与无关功能隔离，并写出独立验证与回退边界。
- 上下文负载为 2 或结论为“高”时已继续拆分，没有直接交给单个开发窗口。
- 每期核心必读只包含直接相关章节、上期交接和 2–6 个关键代码入口；次要材料按需读取，没有要求加载全部仓库和全部历史文档。
- 每期写明预计阻塞点、阻塞快照和动态拆期条件；实际负载超限时允许停在可验证边界重新拆分，不强行在原窗口完成。
- 每期在 Git 备份前填写阶段交接记录，下一窗口能凭仓库、主需求文档、交接记录和阶段标签继续，不依赖旧聊天记忆。
- 工作量评分用于 AI 执行负担，没有用“预计几小时 / 几天”代替评分依据。

## Git 代码检查点与远程备份

- 生成分期文档前已现场检查 Git 状态；Git 可用时进一步核对工作区、具名分支、目标远程、远程访问和推送条件，没有只凭 `.git` 或 README 判定。
- Git 不可用时没有擅自初始化仓库或宣称存在恢复锚点；只记录变更文件与期初 / 期末哈希用于核对，并把恢复能力写为“无”。
- 主需求文档和分期 README 写明保存策略、远程写入授权、远程与分支、代码标签规则和数据 / 外部状态回退路径。
- 远程 URL、检测结果和交付记录没有回显令牌、密码、私钥或带凭据 URL。
- Git 代码检查点没有单独拆期，也没有作为扩大产品范围的依据。
- 每期开始要求记录 `BASE_SHA` 与期初工作区，明确禁止覆盖、丢弃或混入用户原有改动。
- 每期结束按保存策略执行敏感信息检查、精确暂存、本地提交 / 标签；只有明确授权远程才推送验证。没有使用 `git add .`、`git add -A`、强推或移动旧标签。
- 真实或高度疑似敏感信息一律阻止进入 Git，没有提供“用户允许后上传”的分支。
- 远程存在、可访问和凭据可用没有被当作推送授权；授权限定到明确仓库、远程、分支和任务范围。
- 推送失败时保留本地成果并标记“开发验收通过，本地检查点完成，远程备份失败”，没有强推。
- 交付要求包含完整提交号、阶段标签、本地 / 远程状态和未保存原因；代码恢复优先从阶段标签新建分支。
- 涉及数据库、生产数据或第三方副作用时有单独回退 / 补偿方案，没有把 Git 标签写成业务状态精确回滚。

## 包工头施工（施工中 / 每轮结束时核对）

- 包工头没有亲自写产品代码、重做验收或替子 agent 跑测试；规划、关键事实查实、需要凭据的线上操作和交接由包工头亲自做了。
- 开工前查过现场（陌生提交、未提交改动、换电脑后的环境）和文档与现状的差异；本批要用户决定的事编号一次问清。
- 有分批计划表，停点在完整的功能环节；有额度上限时按实测消耗估算并守住刹车线。
- 子 agent 自加的规则已交用户拍板；用户含糊的答复已核实，概括式答复已写明理解。
- 每份开发任务书含必读路径、范围与地盘、测试纪律、Git 纪律、红线、交付格式与状态文件路径；没有粘贴整份需求文档，没有写入任何口令或密钥。
- 文档写得较早的期次，任务书要求先核对文档与代码现状差异。
- 需要用户拍板的事项已翻成业务话、给了具体例子和推荐；用户原话原样转给了子 agent 并记进需求证据。
- 线上操作由包工头直接完成，没有把命令和表单甩给用户；凭据没有打印、进对话或交给子 agent。
- 不可撤回、花钱、动共用设施的操作开工前问过用户；被工具拦下时没有绕过，请用户切确认模式处理；没有修改开发工具自身的权限设置；不得已交给用户的命令包工头已逐行核对。
- 涉及钱的期次做完已派监理，结论带“文件:行号”和触发场景；问题由施工队先写测试复现再修。
- 并行期次地盘不重叠，共用文档同一时间只有一方在写；客户端与服务端并行后补过一次真实联调。
- 每期收尾后 README 期次状态已更新，遗留项写清；用户收到了简报。
- skill 与任务书里只写模型系列名；Codex 施工时 `.codex/agents/` 已放好角色文件并填入当前最新型号，施工队没有继承包工头的最强模型。
- 一轮结束时有《包工头工作记录》，含结果、用户决定、待办（等决定 / 等实测或材料 / 技术）、事故与教训、后续计划和新包工头开场提示词；没有重复抄写前几轮仍有效的内容。
- 交接是包工头主动提出的；交接前没有留下仍在运行的子 agent，临时状态文件里有用的内容已抄进记录；中途停下的期次写了“进行中的期次”；交接记录已提交推送。
- 交给用户的最后一条消息写明了新窗口用哪个档位，并贴出完整开场提示词；开场提示词要求新包工头先汇报现状与待决定事项再派活。
- 交接后又有进展的，已追加“交接后补记”并重新提交。

## 通病
- 无“一律 / 全部”式一刀切；多平台 / 多档位分情况。
- 区分产品能力与实现手段，未把换手段说成砍功能。
- 参考项目 / 竞品的判断有代码 + 行号佐证，非凭 README / 片段。
- 未自创结构，沿用现有目录、命名、组件、端口（以项目档案与仓库现状为准）。
- 未把模板中的示例能力当成默认需求，也未把待确认问题直接排进开发计划。
