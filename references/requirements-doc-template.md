# 功能开发需求文档模板

用这个模板写“主需求文档”。目标是让后续开发 AI 看到文档后，能按项目现状施工，而不是重新发明需求结构。

> **术语替换与裁剪（先读）**
> 本模板按“多层架构 + 多数据库 + 云端密钥 + 计费 / 白名单”的最复杂情形给结构。写文档时：
> - 占位符 `{{前端}}`、`{{本地后端}}`、`{{云端后端}}`、`{{主库}}`、`{{次库}}`、`{{鉴权方案}}`、`{{白名单机制}}`、`{{结构检索工具}}` 从**项目档案**取真实名替换。
> - 项目档案里没有的层 / 库 / 机制，直接删掉对应小节，别为凑结构硬造需求。单体项目就写单层，无云端就不写云端，无计费就写“不计费”。
> - 模板列举的是检查维度，不是默认功能清单。只有“用户 / 现有材料已确认”或“主链路不可缺少的必要配套”才能写入本次功能、任务、验收和期次。
> - 简单需求可以合并或删除不适用章节；某类技术不涉及时，一句话写“不涉及 / 保持不变”，不要为了补齐 11 节设计新接口、新表或新流程。
> - 无论需求大小，标题后面的“0. 业务需求共识”都不能删除或移到技术章节之后。它是给用户确认 AI 是否理解正确的，不是写给开发人员看的技术摘要。
>
> **上游物料前置（必做）**
> 动笔前按文档强度建立需求证据（模板见 `references/raw-requirements-template.md`）。轻量模式可把关键证据内嵌在任务记录或精简主文档中，不强制新建 `00` 文件；标准 / 审计模式独立产出《需求证据与原始描述参考》。原话档案负责举证，不是最终执行基线；执行优先级为“当前有效决策 → 已确认最终效果与验收场景 → 本文件 → 分期提示词 → 原话证据”。范围、决策、不做项和待确认问题要标注 `U/P/A/E/D` 来源。
>
> **从无到有的界面需求：内容一次写全，版本状态区分成熟度**
> 完整读取 `references/visual-first-workflow.md`。**不要因为原型未确认就停笔或留白**：全部适用章节和期 0 到期 N 的期次一次写完，涉及页面形态、数据契约和交互结论的部分标注“待视觉确认复核”，并写清它会因确认结果如何改变。此时文档版本为 `v0.9 待视觉确认基线`。用户在本地预览确认、修改项闭环、门槛线之后的期次复核完成后，去掉标注并升为 `v1.0 已确认开发基线`。
>
> 视觉确认门槛拦的是**代码施工**，不是文档编写。用户确认是跨会话的长动作，把整份需求吊在上面会导致需求搁置、上下文膨胀和后续断层。

```markdown
- 适用范围：

- 业务确认状态：待确认 / 已确认（YYYY-MM-DD）/ 阻塞确认
```

## 0. 业务需求共识（开头必写）

本节只用普通人能听懂的业务语言。不要出现类名、方法名、表名、字段名、API 路径、队列等开发术语；确实需要提及时，先说用户能感知的影响，再在括号里补技术名。

明确区分：

- **原始目的**回答“为什么要做、想解决什么问题”。
- **原始目标**回答“用户最开始想做到什么”。
- **最终期望效果**回答“经过多轮沟通后，AI 当前理解为最终要交付什么”。
- 原始目标保留为历史记录，不能被最终方案覆盖或改写。

```markdown
## 0. 业务需求共识（请先确认）

> 本节根据《需求证据与原始描述参考》和当前决策台账形成。原话用于回查历史；执行时以当前有效的 `D-xxx`、已确认最终效果和验收场景为准。

### 0.1 一句话大白话
<谁在什么场景遇到什么问题，希望通过本功能完成什么，最后得到什么结果。>（来源：U-xxx）

### 0.2 用户提出需求的原始目的
- 想解决的问题：<用户为什么提出需求；未说明就写“未明确说明，待确认”>（来源：U-xxx）
- 业务价值：<省时间、减少错误、降低成本、完成某项业务等；没有依据不要编造>（来源：U-xxx）

### 0.3 用户最开始提出的原始目标
- 使用者：<谁使用>（来源：U-xxx）
- 原始操作与结果：<用户最初希望怎么做、得到什么>（来源：U-xxx）
- 原始明确边界：<最开始明确不要什么；没有则写“未明确”>（来源：U-xxx）

### 0.4 AI 当前理解的最终期望效果
- 使用者最终从哪里开始：<页面 / 业务入口，用业务名称>（来源：U-xxx）
- 用户要做什么：<关键动作>（来源：U-xxx）
- 系统最后给用户什么结果：<用户能看到、拿到或继续完成什么>（来源：U-xxx）
- 哪些现有业务保持不变：<与本次直接相关的保留项>（来源：U-xxx）
- 明确不包含：<已经确认不做的能力>（来源：U-xxx）

| 用户的原话说法 | 来源编号 | 强调次数 | 当前结论 | 本文件落地位置 |
|---|---|---:|---|---|
| <引用用户原话短句，不要改写成概括> | U-014, U-027, U-041 | 3 | 本次必须 / 待确认 / 已明确不做 | §1.3 范围表第 N 条 |

没有时写：“本次沟通中未出现重复强调的诉求。”

### 0.6 多轮沟通中的需求演变与冲突
| 轮次 / 来源 | 来源编号 | 当时的说法或目标 | 变化类型 | 对最终效果的影响 | 确认状态 |
|---|---|---|---|---|---|
| 初始需求 | U-001 | <原始目标> | 原始版本 | <作为对照基线> | 已记录 |
| 后续沟通 | U-032 | <补充或不同说法> | 补充 / 明确替换 / 冲突 | <最终增加、取消或尚不确定什么> | 已确认 / 待确认 / 阻塞确认 |

没有演变或冲突时明确写：“当前需求与原始目标一致，暂无需求演变或冲突。”

存在“待确认 / 阻塞确认”时，本节必须把两端原话**原样贴出**并说明各自的业务后果，等用户直接选；不得替用户选，不得同时保留两个分支假装兼容，不得用“综合考虑后按 X 处理”这类表述掩盖分歧。

### 0.7 请用户确认

- 原型前最小业务草案是否已确认：是 / 否
- 是否需要期 0 技术探针：否 / 是，需核实 <会阻塞页面成立的事实>
- 文档产出方式：期 0 到期 N 已一次写完，门槛线之后的期次标注“待视觉确认复核”
- 视觉确认门槛线位置：期 1 之后 / 期 <N> 之后
- 当前允许施工的期次：仅期 0 / 期 0 至门槛线（含期 1 原型）/ 已完成确认与复核，全部期次可施工
- 原型施工授权：仅编写文档，不改产品代码 / 已获授权，可实际施工
- 本地预览入口：<启动命令 + 预览地址；详见期 1 提示词的“本地预览与用户确认”>
- 涉及视觉的技术章节状态：待视觉确认复核 / 已复核冻结（YYYY-MM-DD）
- 门槛线之后期次的复核结论：未复核 / 无实质变更 / 已更新 <期次> / 已作废重拆 <期次>
```

判断规则：

- 本节每一条都要有 `U/P/A/D` 需求或决策来源；代码和外部事实使用 `E-xxx`，不得冒充用户目的或价值。技术限制只能写成实现约束；确实做不到时写入待确认并说明业务影响。
- 用户明确说“改为 / 取消 / 以新方案为准”时，可以把后续说法标为“明确替换”，但仍保留原始目标。
- 后续说法只是设想、语气不确定，或同时保留两种互斥结果时，标为“待确认 / 阻塞确认”，不要替用户选。
- 会改变使用者、业务结果、主流程、权限、计费、数据归属、删除范围或系统边界的冲突未解决时，后续技术章节只能写草案，正式实现计划写“待业务共识确认后再拆分”；只有专门用于解除该冲突的最小探针或备选视觉原型可以在用户知情下先行。
- 只有当前一轮材料时也要写本节，并明确“暂无需求演变或冲突”；不要为了填表虚构历史。

## 1. 背景与目标

这一节承接第 0 节，不得重新解释成不同的业务目标。写清：

- 现状：现在用户怎么做、哪里慢、哪里错、哪里成本高、哪些旧链路要弃用。
- 目标：重构或新建后，用户能完成什么闭环。
- 范围：哪些能力纳入本次，依据是什么；哪些明确不做。
- 原则：UI 风格、数据归属、计费、复用现有能力、不要自造链路等，只写与本次相关的约束。

示例结构：

```markdown
## 1. 背景与目标

### 1.1 现状（要保留 / 要弃用）
### 1.2 重构目标
### 1.3 本次范围与依据
| 能力 / 改动 | 准入类型 | 来源编号 | 依据 |
|---|---|---|---|
| <功能点> | 明确需求 / 必要配套 | U-014, U-015 | <用户原话、文档、代码事实，或缺少它为何无法完成主链路> |

> 每一行都必须有来源编号。必要配套没有直接原话时，写它服务于哪条编号（如“配套 U-014”）。凑不出来源编号的行说明是 AI 自己加的，移出本次范围。

### 1.4 明确不做
| 不做的内容 | 来源编号 | 原因 |
|---|---|---|
| <用户否定过的能力，尽量引用原话说法> | U-016 | 用户明确否定 / 本次范围外 / 无准入依据 |

> 用户明确说过“不要 / 不用 / 别做 / 不是这个意思”的内容必须出现在这里，不得因为“顺手就能做”“做了更完整”又加回去。

### 1.5 设计原则

### 1.6 关键假设与验证
| 假设 | 来源编号 | 当前证据 | 假设错误的影响 | 验证时机与方式 | 状态 |
|---|---|---|---|---|---|
| <关于用户、数据、技术或业务的假设> | U-xxx / E-xxx | <已有证据或“暂无”> | <会返工什么> | 原型前 / 原型确认 / 开发期 / 上线后观察 | 待验证 / 已证实 / 已推翻 |

### 1.7 成功信号
| 层级 | 怎样算成功 | 证明材料 | 来源编号 |
|---|---|---|---|
| 用户结果 | <用户能完成什么，不编造企业 KPI> | 页面走查 / 用户确认 / 使用数据 | U-xxx / D-xxx |
| 开发完成 | <哪些行为和质量门槛满足> | 自动测试 / 构建 / 截图 / 日志 | D-xxx / E-xxx |
```

“可选建议”如确有价值，单独放在文末并标注“不纳入本次”；不要把它写入范围表、开发计划或验收标准。

## 2. 当前决策台账

把当前生效和已被替代的产品 / 技术选择写成表格。这是执行真相；原话和技术证据只负责说明决定从哪里来。

```markdown
## 2. 当前决策台账

| 决策编号 | 决策点 | 当前结论 | 状态 | 需求 / 证据来源 | 理由 | 生效日期 | 替代关系 |
|---|---|---|---|---|---|---|---|
| D-001 | <例如密钥放哪里> | <云端 / 本地> | 当前有效 / 待确认 / 已被替代 | U-021 / E-003 | <理由> | YYYY-MM-DD | 无 / 被 D-004 替代 |
```

只有“当前有效”的决定指导开发。没有确认的内容标为待确认；旧决定保留并标明被哪个新决定替代，不删除历史。

## 3. 整体架构

按项目真实运行档位写，不要只画单体架构（除非项目本就是单体，则如实写单层）。

```markdown
## 3. 整体架构

### 3.1 分层拓扑
{{前端}} -> {{本地后端}} -> {{云端后端}}
（层数按项目档案；单体只写一层，两层就写两层，不硬套三层）

### 3.2 业务链路
用文本流程图写主链路，以及本次确实涉及的失败 / 异步 / 补充链路。
```

按本次实际触达的层说明：

- 涉及外部调用时，前端是否直连外部域名。
- 涉及本地后端时，它负责哪些本地数据和任务。
- 涉及云端时，它负责哪些密钥、第三方调用、计费或账号能力。
- 涉及耗时或异步任务时，由 worker / HostedService / 队列负责，还是同步返回。

## 4. 功能与交互设计

面向用户写页面如何变化。不要只写接口。

本节是前端原型期的施工依据（见 §9.0）：原型要先按这里描述的页面、状态和交互做出来给用户看。本节内容照常一次写全，未经用户在真实页面确认的部分标注“待视觉确认复核”，并写清它会因确认结果如何改变。**用户在原型上确认或推翻的结论，回写到本节、§0.4 和当前决策台账，并注明确认日期与版本锚点**；原型、文档和当前决策不一致时视为阻塞，完成对账后再继续，不能让任一旧产物自动覆盖用户的新确认。

按本次范围选择覆盖：

- 实际新增或变化的页面入口、操作区、按钮和弹窗。
- 实际变化的列表 / 表格列、状态标签和操作按钮。
- 主链路会遇到的加载、成功、失败和无结果状态。
- 新功能如何进入已确认的现有下游链路。
- 搜索、筛选、批量、分页、上传、外链等只有在范围表已准入时才写。

```markdown
## 4. 功能与交互设计

### 4.1 <主入口 / 主流程>
### 4.2 <列表 / 结果区>
### 4.3 空状态与反馈

### 4.4 场景化验收
| 场景 | 前提 | 用户操作 | 用户看到的结果 | 证明材料 | 来源编号 |
|---|---|---|---|---|---|
| <正常 / 空数据 / 加载 / 失败 / 关键边界> | <开始状态> | <具体动作> | <可观察结果> | 自动测试 / 截图 / 日志 / 用户确认 | U-xxx / D-xxx |
```

## 5. 复用与弃用清单

明确哪些复用、哪些替换、哪些不能误删。没有替换或清理时简要写“保持不变”；只有已确认要清理旧系统时才展开删除清单。

```markdown
## 5. 复用与弃用清单

### 5.1 复用
| 模块 | 文件 / 能力 | 用途 |

### 5.2 替换
- <页面 / 接口 / 服务>

### 5.3 清理
- 删除前先用 {{结构检索工具}} / 搜索核对依赖。
- 列出后端、前端、表结构、脚本、文档同步项。

### 5.4 必须保留
- <新链路依赖>
- <下游功能>
```

## 6. 数据模型设计

主库默认 `{{主库}}`；如有次库 `{{次库}}`，写清是否需要两边都改。

不涉及数据结构时，直接写“复用现有数据，无需改表 / 字段 / 索引 / 迁移”，不要为功能增加记录表、历史表、配置表或埋点字段。

涉及数据结构时才覆盖：

- 新增表或新增字段。
- 字段含义、枚举取值、索引、唯一约束。
- 用户隔离字段（项目档案里登记的隔离字段，如 `OwnerType` / `UID`）。
- 加列 / 建表约定（按项目档案，如幂等建表或 `ALTER ADD COLUMN`、迁移工具用法）。
- 多库差异（如唯一索引对多 NULL 的处理、过滤索引等）。
- 是否有生产数据迁移；没有证据时写“需确认”。

## 7. 接口设计

不涉及接口变更时，直接写“复用现有接口，无新增 / 修改”，不要为方便实现额外设计接口。涉及接口时，按本次实际触达的层分开写。

```markdown
## 7. 接口设计

### 7.1 {{本地后端}} 新增
| 方法 | 路径 | 入参 | 返回 | 说明 |

### 7.2 {{云端后端}} 新增（如涉及）
| 方法 | 路径 | 入参 | 返回 | 说明 |

### 7.3 鉴权与计费
```

新增或修改接口时说明：

- Controller / 路由放哪个目录。
- 用 `{{鉴权方案}}` 里的哪种（从项目档案取，如某种 scheme / JWT / 单一鉴权）。
- 是否需要加入 `{{白名单机制}}`（如按运行档位暴露控制器的白名单；无此机制则删掉）。
- 是否计费；如果不计费，明确“不接入计费”。
- 只有相关时才写幂等、重试、异步状态和失败原因；不要为满足模板引入异步或重试机制。

## 8. 技术选型或第三方接口

只有在确实涉及新库、模型、第三方平台时写。格式要可验证：

- 选型结论。
- 为什么这样选。
- 依赖体积、打包、权限、成本。
- 调研日期、接口路径、请求方式、关键参数、返回字段。
- 易踩坑。

没有实测的接口写“需开发前调研”，不要写成已实测。

## 9. 分期开发计划

拆期前先过两道闸门：一是标准 / 审计模式的证据销账表不存在“无归属”；二是第 0 节不存在业务阻塞。这两道闸门管的是“方向是否已定”，未过时不生成正式实现期。

视觉形态未确认不属于闸门，而是门槛线：**期 0 到期 N 的期次一次写完**，在期 1 之后划出视觉确认门槛线，门槛线之后的期次标注“待视觉确认复核”。它们的状态是“方案已成型，待原型确认后复核”，不是“已冻结计划”，也不是“不写”。

**先列交付包，再拆期。** 交付包是用户能实际用上的业务结果，按纵向切片排序，门槛线之后第一个交付包是最短的真实端到端链路。期次服务于 AI 的执行稳定性，不是按业务功能机械分组：同一交付包可以拆成多个技术执行期（最多 4 期）；一期也可以只完成调研证据、稳定契约、风险隔离或迁移验证，只要它解决独立问题、有下游直接使用的持久化产物并能独立核对。防御和验证与真实风险相称，理论极端情况写进“已知限制”。

**视觉先行（从无到有且有界面时必做）**：完整规则见 `references/visual-first-workflow.md`。期 1 使用正式前端代码和可替换模拟数据制作可交互原型；必要时可在它之前安排最小期 0 技术探针。期 1 完成后唤起本地预览入口交用户实测；用户确认、修改闭环并复核门槛线之后的期次后，才开始后端施工并把文档升为 v1.0。

拆期顺序：

1. 从最终期望效果列出交付包（做完后谁在哪里能做什么），排出纵向切片顺序；再从已准入范围中列出调研、确认、设计、代码、数据、测试、迁移、清理等任务原子。
2. 判定是否需要前端原型期（见 §9.0），需要时把它固定为期1，并在它之后划出视觉确认门槛线。
3. 标记依赖、未知信息、风险、影响模块和验收方式，先画单向依赖再组合期次。
4. 给每个候选期次做六维评分：变更面、跨层依赖、不确定性、数据 / 安全风险、验收复杂度、上下文负载，各 0–2 分。要新建或改变界面而用户尚未做过视觉确认时，不确定性记 2 分。
5. 普通开发期控制在 4–7 分；8 分以上按“减负 → 换方案 → 拆一层”处理，不出现多层拆分编号；多期中的 0–3 分轻量期原则上并入相邻期，独立调研 / 确认、高风险迁移或清理检查点可写明理由后保留。
6. 普通开发期最高分与最低分差不超过 3。不要出现前一期承担绝大多数开发，后几期只剩零碎补丁。
7. 每期只解决一个主要问题，安排 3–6 个核心任务包，完成后保持可构建、可验证、可继续开发。
8. 已确认的旧体系清理放在新链路跑通后；可选优化和未来设想不能用于平衡分数或凑期次。

评分覆盖读取核心材料、理解业务、实现、验收、交接和备份的整期负担，不只看代码量；它用于衡量 AI 单窗口负担，不是开发工时。不要写“预计几小时 / 几天”代替工作量依据。

```markdown
### 9.0 前端视觉确认判定与门槛线

- 本次是否从无到有或明显改变用户可见流程：是 / 否
- 是否设立前端原型期：设立（期1）/ 豁免
- 豁免依据（豁免时必填并给出具体事实）：
  - 没有用户可见界面
  - 明确 BUG 且没有新增视觉结构、布局、状态或交互决策（文案纠错可改变文字像素）
  - 完全复用用户已经确认的现有页面、组件和交互，没有新的视觉决策
- 是否需要期 0 技术探针：否 / 是，需先核实 <数据、第三方、性能或安全事实>
- 视觉确认门槛线位置：期 1 之后 / 期 <N> 之后
- 门槛线之前的期次（可立即施工）：<期0, 期1 ...>
- 门槛线之后的期次（确认并复核后施工）：<期2 ... 期N>
- 原型要承载的页面与主链路：<先给用户看什么>
- 本地预览方式：<启动命令 + 预览入口；从项目档案取真实值，详见期 1 提示词的“本地预览与用户确认”>
- 模拟数据形态核对结论：<区分已有系统已核实 / 新功能待设计 / 未知；关键字段、数据量、响应时间和失败方式>
- 后端施工放行条件：用户在本地预览确认通过、修改项闭环、确认记录具有版本锚点、门槛线之后的期次已复核
- 用户视觉确认状态：未开始 / 已确认（YYYY-MM-DD）/ 有修改项待闭环
- 门槛线之后期次的复核结论：未复核 / 无实质变更 / 已更新 <期次> / 已作废重拆 <期次>

> 技术可行性不确定不是永久豁免：先完成最小期 0 探针，随后仍回到视觉原型。豁免但仍涉及现有界面时，要在实现期保留页面截图或走查；纯后端 / 无界面任务不强求截图。
>
> **门槛线只拦施工。** 期 0 到期 N 的期次文档在同一次输出中写完；门槛线之后的期次照常写清任务、数据模型、接口和验收，只标注“待视觉确认复核”。不允许只写到期 1 就停笔等确认。

### 9.1 分期工作量评估

|---|---|---|---|---:|---|---|

平衡结论：
- 普通开发期分数范围：<最低分>–<最高分>
- 是否存在 8 分以上重期：无 / 有，减负与换方案后仍超标，已拆为 <期次>（只拆一层）
- 最大交付包期数：<N>（上限 4）
- 是否存在无理由的 0–3 分轻期：无 / 有，已合并到 <期次>
```

## 10. 决策变更摘要

从 §2 当前决策台账摘出本版本新增、确认、推翻或替代的决定，便于后续窗口快速恢复：

| 决策编号 | 本版本变化 | 旧状态 / 结论 | 新状态 / 结论 | 依据 | 日期 |
|---|---|---|---|---|---|
| D-xxx | 新增 / 确认 / 替代 / 撤销 | <内容> | <内容> | U-xxx / E-xxx / 用户视觉确认版本 | YYYY-MM-DD |

## 11. 风险与对策

只列与本次变更直接相关、确有依据的风险，不按类别凑数量。例如：

- 确实调用第三方服务时，写失败或成本风险。
- 确实存在异步任务时，写重启 / 卡状态风险。
- 确实删除旧代码时，写连带影响。
- 确实变更数据库时，写索引 / 迁移风险。
- 本次交互直接触达的异常输入和前端反馈风险。

## 待确认问题

只有确实没证据且答案会影响本次方案时添加。不要为了显得完整而阻塞明确需求，也不要把可选扩展包装成待确认问题。

```markdown
## 待确认问题

1. <问题>（来源：U-006）：影响 <范围>，建议确认 <选项A / 选项B>。
```

原话之间存在矛盾而产生的问题，必须把两端原话**原样贴出**，说明各自会导致什么不同的业务结果，让用户直接选；不得只写 AI 的倾向，不得含糊表述。

## 交付前闸门：证据销账核对

标准 / 审计模式的主需求文档写完后，回到《需求证据与原始描述参考》第 6 节逐条登记每个编号的去向，并把结论同步到本文件元信息和 §0.7。

- 去向只能是五种之一：**已写入 / 已明确不做 / 待确认 / 阻塞确认 / 非需求上下文**。
- 存在“无归属”时可以交付 `v0.9 待视觉确认基线`供用户继续澄清，但不得冻结 `v1.0` 或开始正式实现期的施工。
- 寒暄、纯调试指令或与业务结果无关的内容可标“非需求上下文”，但必须写明依据，不能借此丢掉真实约束。
- §0.5 高关注清单里的每一条必须有当前处理结论；写成“已明确不做”时要有用户确认的 `D-xxx`。

```markdown
## 证据销账核对结论
- 原话总数：<N> 条
- 已写入 <N> · 已明确不做 <N> · 待确认 <N> · 阻塞确认 <N> · 非需求上下文 <N> · 无归属 **0**
- 高关注项是否全部有当前处理结论：是 / 否
- 明细见：轻量模式填本文件内嵌章节或任务记录路径；标准 / 审计模式填 `docs/<功能名称>/00-需求证据与原话参考.md` 第 6 节
```
