# 视觉先行需求发现工作流

本工作流适用于面向普通用户或产品经理的 vibe coding 需求。视觉原型不是开发完成后的展示物，而是帮助用户发现、表达和确认需求的工具。

**先记住一条总纲：视觉确认门槛拦的是代码施工，不是文档编写。** 需求文档和全部期次一次性写完，门槛以期次形式落在文档里。

## 目录

1. 适用判定
2. 技术可行性不确定时的期 0
3. 正确顺序：文档一次写完，施工分段放行
4. 原型前最小业务草案
5. 原型施工边界
6. 数据形态与体验契约
7. 视觉确认门槛与本地预览
8. 用户确认与版本锚点
9. 确认后的复核与冻结
10. 输出前检查

## 一、适用判定

同时满足以下条件时，视觉先行是强制规则：

- 本次是从无到有的新能力，或明显改变已有用户流程。
- 最终存在用户可见页面、交互或状态反馈。
- 用户尚未确认过具体视觉形态和操作路径。

第一个可供用户评审的开发产物必须是项目正式前端中的可交互视觉原型。不得先投入正式后端底座、数据库迁移、鉴权接入或完整接口建设。这条约束针对**代码施工顺序**；需求文档和后端期次的编写不受它限制，见第三节。

只有以下情况可以豁免：

1. 没有用户可见界面，例如纯接口、定时任务、数据迁移或后台清理。
2. 明确 BUG 修复，没有新增视觉结构、布局、状态或交互决策，例如目标位置和目标文案均已明确的错别字修复。
3. 明确功能升级，完全复用已确认的现有页面、组件和交互形态，没有新的视觉决策。

“功能升级”不是天然豁免理由。只要布局、操作顺序、页面状态、关键反馈或主流程发生明显变化，仍需视觉先行。

**中途升级时用户已看过的页面**：本来当小改动直接在做、中途升级为包工头的需求，用户已经在真实页面上看过并认可的部分视为已确认，不补做原型。在原型期的《前端确认记录》位置记下：版本锚点（升级时的存档提交号）、页面入口、用户认可的原话；截图由施工队补拍。用户看过但仍在提修改的部分不算已确认；升级后才出现的新页面、新流程仍须视觉先行。

## 二、技术可行性不确定时的期 0

如果页面能否成立首先取决于数据能否取得、第三方接口是否支持、性能是否可接受或安全边界是否允许，可以先设“期 0 技术探针”。

期 0 只能回答会阻塞视觉方案的少数事实：

- 目标数据或能力是否存在。
- 关键字段、数据规模和典型响应时间。
- 无法绕开的权限、成本或平台限制。
- 哪些视觉设想技术上不可成立。

常规读取代码、接口文档和现有数据样本属于需求调研，不自动成为期 0。只有需要独立执行验证、结果会决定原型能否成立时才设期 0。

期 0 必须保持最小、对业务与生产状态默认只读、可丢弃，不建设正式业务底座。验证性能、第三方能力或权限时，可以在已授权的沙箱 / 测试环境发起受控请求；未经明确授权不得写业务数据、产生费用或触发外部副作用，任何情况下都不做不可逆操作。测试范围、环境和结果要留证。探针结论形成持久化证据后，下一步仍然是视觉原型，而不是直接进入完整后端开发。

## 三、正确顺序：文档一次写完，施工分段放行

用户确认原型是一个跨会话的长动作。把整份需求文档挂起来等它，会造成三个后果：已经谈清楚的需求被长期搁置；确认结束时聊天上下文已经过大；后续期次因记忆断层反复返工。所以确认门槛拦的是代码施工，不是文档编写。

从无到有且有界面的需求按以下顺序推进：

1. 整理需求证据并处理敏感信息。
2. 形成原型前最小业务草案，冻结方向和边界。
3. 必要时执行期 0 技术探针。
4. **一次性写完整套文档**：主需求文档的全部适用章节，以及期 0 到期 N 的全部期次提示词。中途不因“等用户确认”停笔，也不拆成两次会话生成。
5. 在期次序列上划出视觉确认门槛线：门槛线之前是原型与前端可见效果，门槛线之后是后端、数据、鉴权、集成和迁移。
6. 施工期 1 原型，完成后按第七节唤起本地预览入口，交用户实际测试。
7. 用户基于原型补充、否定和确认需求；新反馈追加进需求证据，更新当前决策台账。
8. 复核门槛线之后已写好的期次：无实质变更原样放行，有实质变更先改文档再施工。
9. 复核通过后执行后端、数据、鉴权、集成、迁移和清理期次。

未经用户在真实页面上验证的技术结论，要写出来并标注“待视觉确认复核”，同时写清它会因确认结果如何改变。不得把这些章节留白、写“待补充”，或以“等用户确认后再写”为由中断文档产出。

已写好但未复核的后端期次不是“已确认计划”。它的状态是“方案已成型，待原型确认后复核”；施工前必须走完第九节的复核步骤。

如果用户当前只要求编写或评审需求文档，把全部期次、授权边界和确认门槛写完整，但不直接修改产品代码。只有用户明确要求构建或修改时，才实际施工原型。

## 四、原型前最小业务草案

原型前只需让用户确认以下内容：

- 谁使用、要解决什么问题。
- 用户从哪里进入、初步主流程是什么。
- 原型准备展示哪些页面、状态和关键动作。
- 已明确不做什么。
- 当前关键假设和待通过原型确认的问题。
- 模拟数据采用什么来源和可信度。

最小业务草案是给用户确认方向的沟通产物，不是主需求文档本身：这一环节不要拿完整表结构、正式接口、鉴权改造和迁移方案去问用户。主需求文档的对应章节照常一次写完，只是标注“待视觉确认复核”。远期扩展则无论在哪里都不写。

## 五、原型施工边界

原型必须满足：

1. 写在项目正式前端目录，沿用现有路由、组件和设计语言。全新项目没有这些基础时，先基于预期投入生产的技术栈创建最小正式脚手架；技术栈、品牌风格或终端形态会显著影响成本和体验时，先把选择写入当前决策台账并请用户确认。
2. 使用可整体替换的模拟数据层，后续接入真实数据时不推倒页面结构。
3. 覆盖正常有数据、空状态、加载中、失败提示和主链路关键动作。
4. 不用一次性静态页面、截图稿或外部设计稿冒充可交互产物。
5. 不建设正式数据库、生产接口、鉴权链路或数据迁移。
6. 允许只读检查代码、接口文档和数据样本，也允许为核实形态做最小可丢弃探针。
7. 模拟数据和调试入口必须通过开发环境开关、依赖注入或等价机制隔离；生产构建验收要确认不存在 mock 数据引用和未授权调试入口。

## 六、数据形态与体验契约

模拟数据内容可以虚构，数据形态不能无依据地假定。原型前记录：

| 项目 | 结论 | 来源类型 | 证据 / 待确认方式 |
|---|---|---|---|
| 关键字段 | <字段及是否必有> | 已有系统已核实 / 新功能待设计 / 未知 | <代码、接口、样本或原型确认> |
| 数据规模 | <典型与上限> | 已核实 / 假设 / 未知 | <证据或验证方式> |
| 响应时间 | <即时 / 数秒 / 长任务> | 已核实 / 假设 / 未知 | <证据或验证方式> |
| 失败方式 | <全部失败 / 部分失败 / 可重试> | 已核实 / 假设 / 未知 | <证据或验证方式> |

已有系统中的字段、数量和响应时间应从现有代码、接口或数据样本核实。全新能力没有现成事实时，把它们写成“体验契约候选”，交用户通过原型确认，不得伪装成已存在的后端事实。

看不清的内容必须在原型和确认记录中标注“数据形态未核实”，并指定后续责任期。

## 七、视觉确认门槛与本地预览

门槛线写在期 1 文档里，不是留在聊天里。期 1 提示词必须包含“本地预览与用户确认”一节，回答四件事：

1. **怎么跑起来**：从项目档案取真实启动命令（`{{验收方式}}`），写完整，不写“启动开发服务器”这类空话。
2. **从哪里进**：本地预览地址和页面入口，例如 `http://localhost:5173/<路径>`；桌面端或移动端写实际打开方式。项目档案没登记时，从代码或配置核实后写进去，不猜端口和路由。
3. **请用户看什么**：按主链路列出要点开的步骤，以及必须看到的正常有数据、空状态、加载中、失败提示和关键动作。不能只丢一个地址让用户自己找。
4. **什么条件才放行**：用户确认通过、修改项闭环、版本锚点完整、门槛线之后的期次复核完成，才允许开始后端施工。

期 1 做完后，由包工头直接唤起本地预览、打开到入口页，再把测试路径翻成编号测试步骤发给用户，不先问用户，也不把启动命令交给用户自己跑。具体做法见 `foreman-workflow.md` 第五节。

模板：

```markdown
## 本地预览与用户确认（本期完成后必须执行）

本期代码完成后不要直接进入下一期。包工头直接唤起本地调试、打开到预览入口（不先问用户），按下表给用户编号测试步骤，交用户实际测试。

### 唤起本地预览
- 启动命令：`<项目档案 {{验收方式}} 的真实命令>`
- 预览入口：`<http://localhost:<端口>/<路径>>` 或 `<桌面端 / 移动端实际打开方式>`
- 前置条件：`<依赖安装、mock 开关、测试账号等；没有就写“无”>`
- 关闭方式与注意事项：`<例如占用端口、需要保持运行；没有就写“无”>`

### 请用户测试的路径
| 序号 | 用户操作 | 应当看到 | 请用户重点看 |
|---|---|---|---|
| 1 | <从入口开始的第一步> | <页面状态或结果> | <布局、顺序、措辞是否符合预期> |
| 2 | <触发空数据的路径> | <空状态提示> | <提示是否说得清下一步做什么> |
| 3 | <触发加载的路径> | <加载中反馈> | <等待期间是否有明确反馈> |
| 4 | <触发失败的路径> | <失败提示与可重试方式> | <用户能否判断出了什么问题> |

### 放行条件（未满足不得开始下一期施工）
- 用户已实际打开预览并逐条走完上表：是 / 否
- 用户确认通过，或提出的修改已全部改完并复看：是 / 否
- “前端确认记录”已填写且版本锚点完整：是 / 否
- 门槛线之后的期次已按确认结果复核：无实质变更 / 已更新 <期次编号> / 已作废重拆 <期次编号>
```

缺少启动命令、预览入口或用户测试路径的原型期文档视为不合格。门槛线之后的每一期，在“前置状态”里回指本节的放行条件。

## 八、用户确认与版本锚点

视觉确认必须绑定用户实际看到的版本：

```markdown
## 前端确认记录
- 演示时间与方式：
- 原型提交号或本地版本标识：
- 页面入口：
- 截图 / 录屏路径：
- 用户是否实际打开本地预览并走完测试路径：
- 用户确认通过的页面、状态与动作：
- 用户当场提出的修改：
- 用户明确否掉的部分：
- 尚未确认或数据形态未核实的部分：
- 新增需求证据编号：
- 修改后复核结果：
- 门槛线之后期次的复核结论：无实质变更 / 已更新 <期次> / 已作废重拆 <期次>
- 最终结论：已确认，可放行后端施工 / 有修改待闭环 / 重做原型
```

优先使用 Git 提交号。无 Git 项目使用不可覆盖的 `prototype-YYYYMMDD-HHmm-<短哈希>` 标识，并记录原型文件清单的 SHA-256、运行命令和截图 / 录屏；“最新版”“当前本地页面”不算可复现锚点。

只有“用户明确确认 + 修改项闭环 + 版本锚点完整 + 后续期次已复核”才允许开始正式后端、数据和鉴权施工。AI 不得根据“页面能打开”或自己的判断代替用户确认。

## 九、确认后的复核与冻结

用户确认后：

1. 新反馈追加进入需求证据，不覆盖历史记录。
2. 更新当前决策台账；被替代的决策保留历史状态和替代原因。
3. 把确认过的页面、状态、动作和明确否定项写入正式需求文档，去掉对应的“待视觉确认复核”标注。
4. **复核门槛线之后已经写好的期次**，逐条判断确认结果是否改变了它们的前提：
   - 无实质变更：在期次文档标注“已按 <确认日期 + 版本锚点> 复核，原样执行”。
   - 有实质变更：先更新受影响的需求章节和期次文档，再开始施工；变更写入决策台账和主需求文档的决策变更摘要。
   - 被推翻：把该期次标为作废并写明原因，重新拆期，不留下与当前确认冲突的旧文档。
5. 补齐可观察的成功信号、场景化验收和技术质量门槛。
6. 依据已确认视觉和体验契约核对数据、接口与技术方案，必要时重做工作量评分。
7. 主需求文档由 `v0.9 待视觉确认基线` 升为 `v1.0 已确认开发基线`，记录确认日期、版本锚点和复核结论。

复核是必做步骤。文档提前写完的代价就是这一步：跳过复核直接施工，等于把用户在原型上说的新话丢在聊天里。

## 十、输出前检查

- 从无到有且有界面的需求是否把期 1 安排为视觉原型期。
- 主需求文档和期 0 到期 N 的期次提示词是否在同一次输出中写完，没有因等待确认而停笔或留白。
- 未经视觉验证的结论是否标注“待视觉确认复核”并写清会如何改变，而不是写成“待补充”。
- 期次序列是否有显式的视觉确认门槛线，门槛线之前是前端可见效果、之后是后端与数据。
- 期 1 文档是否写了“本地预览与用户确认”：真实启动命令、预览入口、用户测试路径和放行条件。
- 门槛线之后的每一期是否在“前置状态”回指放行条件。
- 豁免是否命中明确条件并有事实依据。
- 技术探针是否保持最小，且探针后仍回到视觉原型。
- 模拟数据是否区分“已有事实 / 新设计 / 未知”。
- 是否覆盖正常、空、加载、失败和关键动作。
- mock 与调试入口是否与生产构建隔离。
- 用户确认是否绑定提交号或版本、入口和截图 / 录屏。
- 修改项是否闭环、后续期次是否复核后才开始后端施工。
